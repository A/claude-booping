# booping plugin — project guide

Claude Code plugin that grooms and executes plans across user projects. Plans live in the per-project vault — `~/Claude/{project}/` by default, or a repo-local directory via the `.booping` marker's `vault_path:` key; skills, agents, templates, and config live in this repo.

## Status

_Last updated: 2026-08-05._

Runtime template-rendering pipeline + build-time `src/files/` pipeline are both live. Current state:

- **Build-time skills/agents**: every committed `skills/<name>/SKILL.md` and `agents/<name>.md` is generated from `src/files/<rel>.j2` via `just build` (which calls `bin/booping build`). Frontmatter values that vary across files (today: `effort`) live in `src/config_files.yaml`, a build-only config that is **not** project-overridable.
- **Runtime rendering**: the body of each generated thin shell is a single `!`booping render src/templates/.../<name>.md.j2`` line; bodies are rendered at skill-load time by `bin/booping` (Python uv project at `booping-python/`).
- **Config override tiers**: two runtime override tiers deep-merge over `src/config.yaml` in order **core → global → project** — global (`${XDG_CONFIG_HOME:-~/.config}/booping/config.yaml`) then project (`~/Claude/{project}/config.yaml`). Runtime only; does not affect `config_files.yaml`. There is no schema gate and no per-key tier restriction: no tier drops a key, so a user's own playbook namespace is legal config without a plugin change. The `home_dir` key (vault-home base) is resolvable via `booping config-get home_dir`; `bin/booping-create-project` seeds it into the global tier on first run.
- **Config namespacing**: `src/config.yaml`'s top level is exactly `home_dir` + `core`. Under `core`, a key one playbook owns lives at `core.{name}_playbook`; a key the development loop or several playbooks share sits directly under `core`.
- **Single CLI**: `bin/booping` with subcommands `render`, `render-playbook`, `playbook-state`, `playbook-transition`, `config-get`, `marker-set`, `query`, `scaffold`, `frontmatter-update`, `build`, `debug-context`, `debug-template`.
- **Static docs**: `docs/` is hand-authored (no build step). Nothing under `docs/` is rendered at runtime.

## Layout

- `booping-python/` — uv Python project containing the `booping` CLI (subcommands `render`, `render-playbook`, `playbook-state`, `playbook-transition`, `config-get`, `marker-set`, `query`, `scaffold`, `frontmatter-update`, `build`, `debug-context`, `debug-template`). Source under `booping-python/src/booping/`; tests under `booping-python/tests/`.
- `booping-python/src/booping/context/config.py` — the config loader, and nothing more: `global_config_path()` plus a `load()` that reads `src/config.yaml` and deep-merges each existing override path over it (`agents` shallow-merged). No validation pass, no schema model, no privileged-key filter — a config key the plugin has never heard of loads unchanged in every tier.
- `booping-python/src/booping/context/lifecycle.py` — `resolve_edges` / `resolve_hooks` over a machine dict (`statuses` + optional `superstates`). Generic: its only caller is `playbook-transition`, resolving a playbook's `states:` entry.
- `booping-python/src/booping/query.py` — the one frontmatter loader: spec resolution, glob + slug de-duplication, filtering, sorting, column projection, the `Row` wrapper and the single table writer (`as_table`). No argparse, no Jinja. The `Plan` model and the eagerly-loaded plan list it fed are gone; every listing goes through a query spec.
- `booping-python/src/booping/macros.py` — config-declared argv macros: dotted-path resolution, call-site positional arguments appended to the declared prefix, `subprocess.run` with `shell=False`, a per-process cache keyed by the argv tuple, and `--stub-macro` injection (matched on the path, so it covers every argument variant). Exposed to every rendered body as the `macro()` global; it replaced the old `now()` global.
- `bin/booping` — shell wrapper: resolves plugin root from its own location and exec's `uv run --project booping-python booping "$@"`.
- `bin/booping-create-project` — standalone uv inline script; scaffolds the vault directories + `.booping` marker. Defaults to `~/Claude/{project}/`; with `--local [dir]` (default `./booping`) scaffolds a repo-local vault and writes the `.booping` `vault_path:` key + a vault `.gitignore`. Out of scope for the runtime pipeline.
- `bin/booping-external-llm-call` — standalone uv inline script; renders a Jinja2 prompt template from `bin/llm-call-templates/` and sends it to Gemini. Out of scope for the runtime pipeline.
- `src/config.yaml` — single source of truth for structured data rendered into skills and playbooks at runtime (task types, sprint scale, macros, query specs, scaffold trees, per-playbook agents / status / etc.). Top level is `home_dir` + `core` only. Loaded at render time by `Context.assemble()`. Project-overridable in every key.
- `src/config_files.yaml` — **build-only** config consumed by `bin/booping build`. Carries frontmatter values that vary across `src/files/**/*.j2` templates (today: just `effort` per skill / per agent). **Not** project-overridable.
- `src/files/<rel>.j2` — **build-time templates** for every committed `skills/<name>/SKILL.md` and `agents/<name>.md`. Mirrors the plugin root one-to-one. Each template is a thin shell (frontmatter + a single `!`booping render src/templates/...`` line); rendered by `just build` using `src/config_files.yaml`.
- `src/templates/skills/<name>.md.j2` — runtime skill templates, one per surviving skill (`code-review`, `playbook`). Rendered at skill-load time via `!`booping render ...`` in the generated thin shell.
- `src/templates/agents/<name>.md.j2` — runtime agent templates. Same shape. The developer agent's body lives in `_partials/_developer_body.j2`.
- `src/templates/_partials/_*.j2` — reusable fragments. Include via `{% include %}` (data-only) or import + macro (parameterized). Parameterized partials receive call-site arguments via the `kwargs` namespace. This loader root serves the **skill and agent** env only: a skill body cannot reach `playbooks/_partials/`, which is why the `code-review` skill inlines its own agents table rather than including the shared one.
- `skills/<name>/SKILL.md` — **build artefact** rendered from `src/files/skills/<name>/SKILL.md.j2`. Never hand-edit; edit the `src/files/` template and run `just build`. Two skills ship: `code-review` and `playbook`. `chat`, `help`, `groom`, `develop`, `install`, `retro` and `learn` are all retired — the last five in favour of playbooks, `chat` and `help` outright.
- `agents/<name>.md` — **build artefact** rendered from `src/files/agents/<name>.md.j2`. Same rule.
- `docs/` — **hand-authored static reference docs**, lazy-loaded by skills via `${CLAUDE_PLUGIN_ROOT}/docs/<name>.md` links. Includes `docs/plan_templates/*.md`, `docs/review_templates/*.md`, `docs/template_plan_frontmatter.md`, and `docs/images/`. No build step touches this directory.
- `documentation/` — **end-user docs site source**; per-page markdown consumed by MkDocs (`mkdocs.yml` at repo root). Built and deployed to the `gh-pages` branch by `.github/workflows/docs.yml` on push to `main` (published at `https://A.github.io/claude-booping/`). Distinct from `docs/` (which is plugin-internal lazy-load fragments owned by skills); `documentation/` is the public reference site.
- `migrations/<NNN>_<slug>/migration.md` — **plugin-shipped vault migrations**, one directory per migration. Frontmatter carries `id` (the authority — the `NNN_` directory prefix is a sort hint with no meaning), `title` and `summary`; the body is the procedure the `migrate` playbook performs against a vault. Listed by the `core.migrate_playbook.queries.pending` query spec, which declares `root: core` and so resolves outside any project. A vault's applied watermark is the `.booping` marker's `latest_migration` key (`booping marker-set latest_migration=<id>`, or `=@latest` for the highest shipped id), and every render surface gates on it (see `booping-python/src/booping/migrations.py`). Shipped today: `001_plans_to_dirs`, `002_config_core_namespacing`.
- `~/Claude/{project}/config.yaml` — optional per-project config override; deep-merges over `src/config.yaml` at render time (runtime only).
- `~/.claude/agents/<id>.md` — a project may register **self-contained global agents** as external workers (project-level user config, native to Claude Code; not maintained by the plugin). Wiring details: [documentation/integrating-external-agents.md](documentation/integrating-external-agents.md).
- **Playbooks** — multi-step guided procedures, discovered from three roots: core `<plugin-root>/playbooks/<name>/`, global `<home_dir>/_playbooks/<name>/` (default `~/Claude/_playbooks/`) and local `{vault}/_playbooks/<name>/`. Roots are scanned core → global → local; **playbook names must be unique across roots** — the same name in 2+ roots populates `Playbook.clash_scopes` on the surviving (most specific) entry + a `name_clash` problem, rendered as a blocking STOP and flagged `⚠ clash` in the `/playbook` listing (loading still proceeds local-wins so the listing can show the winner) (`_`-prefixed dirs skipped; a dir without `playbook.md` is skipped silently). Each playbook dir has `playbook.md` (identity: frontmatter `name,title,summary,trigger` + optional `requires_project`, default false — when true the playbook is flagged in the `/playbook` listing and refused, and `render-playbook` errors, unless a booping project is attached) plus an optional `playbook.yaml` carrying the **structure**: `graph:` + optional `state:` (the outer graph's state-machine ref) + optional `states:` (named state machines). `playbook.yaml`'s `graph:` wins; a playbook without `playbook.yaml` falls back to `graph:` in `playbook.md` frontmatter (legacy); declaring `graph:` in both → STOP. `state:`/`states:` are `playbook.yaml`-only. The `graph:` mapping (node name → node) defines membership, order, and parallelism via topological waves (a node joins the earliest wave in which all its deps sit in a prior wave; wave co-members run in parallel and must be `detached:` — a subgraph co-member stands for its whole group, so every one of its inner steps falls under the same rule). A node is **discriminated by value shape**: a list → plain step, the list being its dependency step names; a mapping → **subgraph** with required `dependencies` (outer node names) + required non-empty inner `graph` (inner step name → inner dep names) + optional `repeat` prose + optional `state` (the state-machine ref governing each instance). Exactly **one level** of nesting (a nested subgraph is a STOP); no cross-scope edges (inner deps are inner-only, outer deps see the subgraph as one node); step addressing is flat and step names must be globally unique across scopes (duplicate → STOP), each inner step being a normal `<step>/prompt.md` dir at the playbook root. Inner waves resolve like outer ones; `repeat` is driver-judged prose (absent → one instance), gates fire per instance, and instances run in parallel only when every inner step is `detached:`. **Run state** is opt-in via `states:`: each entry is a named state machine `{artifact, initial, statuses}` (plus optional `superstates`), consumed by `booping.context.lifecycle.resolve_edges`/`resolve_hooks` (`transitions` carry `to,when,gates,hooks`; `terminal: true` ends a branch). `artifact` is a markdown path relative to the **run workdir** (convention `{vault}/_runs/<playbook>/<run-slug>/`, driver-created, unless the playbook names its own — the core `groom` uses the plan directory `{vault}/plans/<slug>/`); a `{instance}` placeholder makes the machine per-instance and is only legal when a subgraph refs it. Hook vocabulary: `frontmatter-update [<file>] <key>=<val>...` (a value is Jinja-rendered with the `macro` global — `completed="{{ macro('core.macros.date', '+%Y-%m-%d %H:%M') }}"`, shlex-tokenised so the quoted expression survives its spaces — plus the literal `@head`; the optional file target is the first `=`-less token, resolved workdir-relative like `artifact`, may carry `{instance}`, must exist or the transition aborts (a file without a frontmatter block gets one bootstrapped) — report line `frontmatter <file>: k=v`) and `script <name>` → `<playbook-dir>/_scripts/<name>`, run with cwd = workdir and `BOOPING_ARTIFACT`/`BOOPING_WORKDIR`/`BOOPING_INSTANCE` in the env (non-zero exit aborts). `status: <to>` is always written before the edge's hooks. `playbook-transition` is the **only** writer of run state and its printed mutation report is authoritative (never re-read to verify); `playbook-state` is the read-only frontier report the driver reads on entry to **resume** (`not-started` → bootstrap on the first transition). No `states:` → the run lives in one conversation and is not resumable. The **body is a preamble** (no step calls) inserted above the rendered procedure. **A step is a directory**: every non-`_` subdirectory of the playbook dir holding a `prompt.md` is a step and the dir name is the step name (frontmatter carries no `name`). Only `prompt.md` is loaded — sibling files (eval configs, fixtures, variants like `prompt.haiku-4-5.md`) are invisible; a non-`_` dir without `prompt.md` warns and is skipped; `_`-prefixed dirs (`_references/`, `_fixtures/`) are free workspace. `prompt.md` carries frontmatter `summary,review_gate` + optional `title` + optional `detached`. Under `jinja: true` the `summary` and `detached` fields are **also** rendered (through the step's own loader chain, same env as the bodies) — so `detached: "{{ config.core.groom_playbook.cross_review_agent or '' }}"` resolves at render time and a `detached` that renders empty (the config key is absent) degrades to runner-performed; a Jinja error in either field is a blocking in-band notice. Bodies (preamble + step prompts) are plain markdown by default; a playbook opts into Jinja for **all** of them with `jinja: true` in the manifest frontmatter, in which case they render through the full context env — rendering without project context, or a Jinja error, becomes a blocking in-band notice. Each Jinja body is rendered with its own `ChoiceLoader` chain, most specific first: **the body itself** (served by basename, so `./x` / `../x` resolve against the including file's own dir at any nesting depth via a `join_path` override) → **step dir** (step bodies only) → **playbook dir** → **the three discovery roots, local → global → core** (so a shared `_lib/` at any root level is includable by root-relative name, with local shadowing global shadowing core) → **`src/templates/`** last, which keeps `{% include "_partials/…" %}` / `{% import %}` resolving plugin-root-relative. Consequence: a `_partials/` inside a playbook dir or root shadows the plugin's for that playbook's bodies (including for `tools.render(...)`, which resolves by name through the same env). Delegation has three levels — **inline** (runner performs the step), **assisted** (runner performs it but delegates heavy reads to the researcher agent; step-body prose, no frontmatter), **detached** (an agent fetches and performs the body; the only level with mechanics). The single `detached` field: absent → runner-performed; `<model>:<effort>` (model ∈ {opus,sonnet,haiku,fable}) → generic sub-agent with that model+effort; any other non-null string → named sub-agent (`subagent_type=<value>`). There is no `null` value — the legacy `agent:` key on a step is a STOP telling the user to rename it. Composed render via `booping render-playbook <name>`: by default no step body is embedded — every section closes on a `booping render-playbook <name> --step <step>` fetch command, for plain and `jinja: true` playbooks alike. A runner-performed step renders the metadata block (`Instructions:` — summary, deps, `Part of:`, gate) closed by `Run … for content.`; under `inline_steps: true` in the manifest frontmatter (or `--inline-steps` on the command) a runner-performed step instead carries its rendered body — step-scoped lessons already appended — in place of **both** the metadata block and the fetch line (summary/deps/gate stay in the step table), while detached steps keep fetch-form so their agents still fetch their own body; those bodies render before the sections are assembled, so a Jinja error in one is an ordinary blocking notice rather than a STOP buried inside a section, and an unwired (orphan) step dir is never rendered and so can never block; a **detached** step renders no bullets at all — summary as a paragraph, `Part of:` / `Review gate:` lines when they apply, then `Tell the `<agent>` agent` (or `Tell a sub-agent — model <m>, effort <e> —`) `to get its instructions by calling this command: …`, deps and wave siblings omitted because the step table already carries them. The driver never fetches a delegated step's body: it spawns the agent with a bootstrap prompt carrying the fetch command ("stdout is your instruction"), `## Run-time context` (project, specs dir, `workdir`/`instance` when applicable), `## Inputs` assembled from run-time context + prior receipts, and a uniform `## Return` contract (artifacts written + outcome, ≤ 5 lines); only non-`detached:` steps are fetched by the driver itself, and subgraph instances each fetch per instance. Subgraphs render as a `## Subgraph: <name>` intro (`After:` / `Repeat:` / `Inner waves:`) followed by their inner step sections (tagged `Part of:`), plus a step-table row tagged `*(subgraph)*` (outer deps + `repeat` prose) whose inner steps follow tagged `*(in <name>)*`. A states-bearing playbook also renders a `## State` section right after `## Playbook Steps`: the `playbook-state` invocation, then per machine its referencing scopes, artifact path, initial status, the exact `playbook-transition` invocation (with `--state`/`--instance` where needed) and a status → to/when/gates table; no `states:` → no section. Graph problems are reported in-band (exit 0): blocking `**STOP — tell the user:**` notices (missing step dir/prompt, dep on unknown step, cycle, missing graph, malformed node, nested subgraph, duplicate step name across scopes, non-`detached:` step in a parallel wave, legacy `agent:` key on a step, `graph:` in both manifests, unparseable/non-mapping `playbook.yaml`, malformed `states:` entry, `state:` ref to an undeclared entry, `jinja: true` without project context, Jinja render error, playbook name defined in 2+ roots — output is then only notices + preamble) and non-blocking `**Note — tell the user:**` warnings (orphan step dir, orphan `states:` entry no scope references, plus the three lesson notices below). Gates are rendered from `review_gate` frontmatter (not authored prose). **Lessons** are markdown files (convention `NNNN_title.md`) in exactly two roots — global `<home_dir>/_lessons/` and project `{vault}/_lessons/` — loaded by `Lesson.load_targeted(home_dir, vault)` into `context.targeted_lessons`, project shadowing global by filename, filename-sorted. Binding is per-file, not per-directory: frontmatter `targets:` is a list (a bare scalar normalizes to a one-entry list) of **exact names** — `{playbook}`, `{playbook}/{step}`, `agent:{id}` — with no globs, wildcards or negation, parsed by `lesson.parse_target` into `parsed_targets` + `target_rejections`. Injection is harness-level, so playbook authors never include a lessons partial: `render-playbook` renders playbook-targeted lessons as `## Lessons` between preamble and `## Playbook Steps` (absent while blocking) and appends step-targeted lessons to `--step` output and to inline step bodies, both through `_partials/_playbook_lessons.j2` (bodies passed as template variables, never Jinja-parsed); `agent:{id}` lessons are injected into the plugin's **internal** agent bodies (`booping-developer`, `booping-researcher`) at load time via `_partials/_agent_lessons.j2` — external/global agents at `~/.claude/agents/` and model-tier sub-agents are out of reach in v1, reachable only by targeting the step they perform. Missing/empty/malformed `targets:` → injected nowhere; lessons are opt-in. Three non-blocking notices: `legacy_lessons` (one full Note line per retired dir still holding markdown — root-level and playbook-level `_lessons/` across the discovery roots, plus the vault's legacy `lessons/` — sorted and deduped), `untargeted_lesson`, `unknown_step_target`. `--no-lessons` suppresses the lesson sections **and** these notices, making output byte-identical to a lesson-free vault. The vault's legacy `lessons/` and `_partials/_lessons.j2` are untouched and still serve the legacy skills. Loaded by `Playbook.load_all(vault, home_dir, plugin_root)` into `context.playbooks` (see `booping-python/src/booping/context/playbook.py`). The driving protocol — render, walk waves, resolve delegation, enforce gates, read/advance run state — lives in `_partials/_playbook_driving.j2`, shared by every skill that drives a playbook (today `/playbook`). The shared eval harness lives in-repo at `playbooks/_lib/` (promptfoo provider, grader, asserts, harness tests) and core playbooks commit their own suites beside their steps (`playbooks/groom/*/`, `playbooks/playbook-authoring/*/` — `tests.yaml` + `promptfooconfig.yaml` + `_fixtures/`, referencing `../../_lib/`); the vault `_playbooks/_lib` is a symlink to the repo copy, and the vault keeps only the run harness (justfile/scripts/docs).
- `playbooks/<name>/` — **core playbooks** shipped with the plugin (the core discovery root), plus the shared eval harness at `playbooks/_lib/` (`_`-prefixed, so not a playbook), the shared partials at `playbooks/_partials/` (today `plans_table.md` — a plans listing any step renders by setting `query_plans` to a query-spec dotted path, with an optional `plans_limit`, default 10 — `task_types.md`, the task-type table over `config.core.task_types` — `timestamps.md`, the run's clock, `{% from "_partials/timestamps.md" import slug_ts, human_ts %}` (imported, not included: `{% set %}` inside an included template does not reach the caller's scope) — `playbook_agents.md`, the **one** delegation table, which a playbook renders by setting `playbook_agents` to its `core.{name}_playbook` config block; both `available_agents` surfaces are gone, and the `code-review` skill carries an inlined equivalent because the skill render env's loader cannot reach `playbooks/` — plus the `learn` routing surface: `lesson_target_toc.md` — every playbook's name, summary and step names plus a literal fetch command — and `lesson_target_space.md`, filtered by `config.targets_for` and fetched via `booping render … --set targets_for=a,b`; an unknown name renders nothing at exit 0 and an unset key renders zero bytes, so the selection logic is template-side and the CLI carries no learn-specific flag) and the render fixture vault at `playbooks/_fixtures/vault/` (a minimal vault — `config.yaml` + empty `plans/` + a `.booping` pinning `latest_migration` — that `--project` resolves against so a render is deterministic and project-independent). Each playbook commits its rendered report at `playbooks/<name>/_reports/output.md`, regenerated by `just playbook-reports`. Today: `playbooks/groom/` — the groom procedure as a `jinja: true` playbook, driven by `/playbook`. Its graph is a six-step chain (`intake` → `research-codebase` → `research-web` → `draft-plan` → `cross-review` → `present`; `draft-plan` deps on both research steps): design work happens in conversation inside `draft-plan`, reference checking lives inside `research-web`, and refinement/decomposition is part of drafting — the old `design` / `decompose-work` / `verify-references` steps are gone. Delegation: **inline** everywhere except `research-codebase` / `research-web`, which are **assisted** (bulk reads delegated to the agent `config.core.research_agent` names), and `cross-review`, which is **detached** via `detached: "{{ config.core.groom_playbook.cross_review_agent or '' }}"` — a second-model review returning severity findings only; with `core.groom_playbook.cross_review_agent` null (the core default) the step's `summary` and body both render as skipped and the runner performs nothing. The playbook sets `inline_steps: true`, so step bodies render embedded in the composed output. **The plan is a directory** — `plans/{slug}/` in the vault (slug `{YYYYMMDDHHMM}_{kebab-title}` per the preamble), which is also the run workdir (no `_runs/`): `index.md` is both the `run` machine's artifact and the plan document itself — `intake` creates it with identity frontmatter (and posts its framing brief in chat / `request.md`), `draft-plan` writes its body against the plan template's Plan Body. Run machine: `framing` → `researching` → `drafting` → `cross-reviewing` → `presenting` → `awaiting-approval` → `ready-for-dev` (terminal), with loopbacks `drafting → researching` and `awaiting-approval → drafting`; superstates `in-spec` / `awaiting-plan-review` / `terminal` group them, and a `script commit-plan` hook on the boundary edges snapshots the plan into the vault git repo. The run has **one review gate**, `awaiting-approval` after `present`: intake's scope answers and draft-plan's in-conversation alignment are the confirmation everywhere else. Its preamble owns groom's transitions table, hard rules, artifact model and in-vault resume mapping; step dirs keep supporting material under `_references/`. **The playbook is now canonical** — the `/groom`, `/develop`, `/install`, `/retro` and `/learn` skills were retired in favour of the `groom`, `develop`, `setup`, `retro` and `learn` playbooks (driven by `/playbook`); with `chat` and `help` retired outright, the surviving skills are `code-review` and `playbook`. Also `playbooks/playbook-authoring/` — the procedure for authoring a new playbook (interview → decompose → states → manifest → a per-step `step-pipeline` subgraph of spec/tests/fixtures/prompt/suite + optimizers, with `record-decision` invoked out of wave order), states-bearing, with its `_specs/` and per-step eval suites committed alongside.

## Information ownership

Every piece of information lives in exactly one of these owners. When you can't decide where something belongs, walk this list top-down.

### `src/config.yaml`

Loaded at skill-load time by `Context.assemble()` — no build step. Three-tier deep merge, **core → global → project**: `src/config.yaml` (core) ← `${XDG_CONFIG_HOME:-~/.config}/booping/config.yaml` (global, resolved by `config.global_config_path()`, env read at call time) ← `~/Claude/{project}/config.yaml` (project). Later tiers win; missing keys fall through; lists replace wholesale (`agents` is shallow-merged). `Config.load()` takes an ordered override-paths list; `Context.assemble` passes `[global_path]` (no project attached) or `[global_path, vault/config.yaml]`. The `home_dir` key (vault-home base for `<home_dir>/<project>/`) is resolved from the core+global partial merge before the project tier, so setting it in the project tier is a no-op; a `.booping` `vault_path:` marker still wins over it. Shell callers read any resolved value via `booping config-get <dotted.key>`. `Context.vault` carries the vault every loader read from — the attached project's directory, or the explicit `vault_override` that `render-playbook --project` passes; it is what the `query` filter resolves globs against, so a render without a vault raises rather than rendering empty. **No key is validated and no key is tier-restricted**: there is no schema gate, no unknown-field warning and no privileged-key filter, so a project config declaring an invented `core.my_playbook.*` block (or its own `core.macros` entry) loads and renders like any other value. A project override of a `core.*` key the plugin ships is the user's to get right.

**Placement rule.** Top level is `home_dir` (it resolves the vault before any namespace is reachable, so it cannot live inside one) plus `core`. Under `core`: a key exactly one playbook owns goes to `core.{name}_playbook`; a key the development loop or several playbooks share goes directly under `core`. `core` is the worked example a user's own playbook namespace copies.

- Structured surfaces skills, playbooks and CLIs consume: task types, sprint scale, macros, query specs, scaffold trees, branch conventions.
- Delegation targets — which agents a playbook may delegate to, declared as `core.{name}_playbook.agents.<id>` entries (built-in workers plus any self-contained global agents the project registers). See [documentation/integrating-external-agents.md](documentation/integrating-external-agents.md).
- The single status a playbook reads to find its queue (`core.{name}_playbook.status`).

Statuses, transitions, gates and hooks are **not** here: each playbook owns its own vocabulary in its `playbooks/<name>/playbook.yaml` `states:` block.

### Skill (`src/templates/skills/<name>.md.j2`)

Instructions, goal, rules, and judgement specific to one skill — the verbs and heuristics for clearing the gates that config defines.

- Verbs and heuristics — *how* to produce the artifacts and clear the gates for the states this skill owns.
- User interaction — what to ask, when, how to present, how to handle approval vs change requests vs cancellation.
- Judgment calls the contract can't pre-specify.
- Invariants the skill enforces across all its states ("Hard rules").

### Shared template fragments (`src/templates/_partials/`, `docs/`)

Content shared across skills/agents, or extracted from a single skill body to keep it lean.

- Cross-cutting guides included into multiple skills or playbooks (git guide, project context, lessons, timestamps).
- Process fragments extracted from a single skill into its own partial (sprint planning, plan-frontmatter shape, task classification).
- Bodies extracted from a single agent into a partial (`_developer_body.j2` for the developer agent).
- Lazy-loaded craft docs (`docs/*.md`) that a skill links into via `[label](${CLAUDE_PLUGIN_ROOT}/docs/<name>.md)` when the situation demands it.

### Project vault (`~/Claude/{project}/`)

Out of framework scope — authored per-project, loaded by skills at runtime.

- Per-skill / per-agent extensions (`_booping/skill_<name>.md`, `_booping/agent_<name>.md`).
- Accumulated lessons — `lessons/` (legacy skills) and `_lessons/` (targeted, playbooks + internal agents).
- Project-local plan templates (`plan_templates/*.md`).
- Project-local review templates (`review_templates/*.md`).

The attached repo's own `CLAUDE.md` is also loaded by skills (it sits in the repo, not the vault) — same role as the above: project conventions the framework reads but doesn't author.

## Principles

- **Minimum useful context**: show only information the skill needs to perform its job. Never bake in stale, speculative, or unrelated data.
- **Less prose, less drift**: every extra sentence in a skill or partial adds tension between what's written and what the model does. Cut motivation, restated context, "you are the skill / you are responsible to" preambles, and any explanation the schema or a referenced doc already carries. The schema is the source of truth; prose decays.
- **Schema over prose**: structured data lives in `src/config.yaml`. If a format or value is there, the skill body must not also describe it in prose — render from config.

## Information hierarchy

When you write a skill, walk these questions top-down for every piece of information you're tempted to inline. Each step moves the cost out of the skill body and into a cheaper mechanism.

1. **Does the skill need this for its main route?** Load it eagerly: inline a CLI fact via `!`command``, or include a static fragment as a partial.
   - Example: project name + path rendered into skill body via `{% include "_partials/_project_context.j2" %}`.
   - Example: the git guide included via the `playbooks/_partials/_git_guide.j2` partial.

2. **Does the skill need this only on a specific route, or only when a condition holds?** Lazy-load with a `[label](${CLAUDE_PLUGIN_ROOT}/docs/<name>.md)` link; the model fetches it when the situation demands it.
   - Example: the `groom` playbook links to per-task-type guidance; only the active type's guide (one of `feature`, `bug`, `refactoring`) is loaded per plan.

3. **Does the skill need the whole, or only one slice?** Split into a partial.
   - Example: the `develop` playbook only needs the plan frontmatter shape; it does not pull in the full plan-template body.

4. **Is this information already available to the skill?** Remove the duplicate.
   - Example: a states-bearing playbook's transitions table is rendered by `render-playbook` from its `states:` block. Step bodies must not restate the flow in their own prose.

5. **Is the value dynamic?** Reference the source, never the literal.
   - Example: the status the `learn` playbook queries to find plans to absorb is named in `src/config.yaml`; the body renders from there rather than spelling the status name in prose.

## Skill design

- **Wide-domain**: skills must work across stacks (Django, Rust, Hugo, etc.). Project-specific concerns live in `~/Claude/{project}/_booping/skill_<name>.md`, `lessons/`, and the project's own `CLAUDE.md` — never in the skill here.
- **Phases over flat sections**: Preflight → High-level workflow → Phase 0..N.
- **Preflight becomes thinner** in template-driven skills: items that were "Read partial X" now appear either as inlined partial content, as `!`command`` blocks, or as lazy `[detailed guidance](${CLAUDE_PLUGIN_ROOT}/docs/…)` links. Preflight is for the things that still require the model to act (e.g. read vault lessons, read `_booping/skill_<name>.md`).
- **Research delegation**: delegate heavy reads / summarization work to `booping-researcher` to protect the skill's context. The agent is for *aggregating many sources into a summary*, not for single-file spot checks — those stay in the skill.
- **Agent wiring**: skills own all reads/writes against `~/Claude/{project}/`. Agents touch only code in the attached repo and never scan the vault. Briefings carry the request, related files, and DoD — no lesson paths. Lesson context reaches agents via two baked-in channels: DoD + Verify pasted from the plan (folded in by the `groom` playbook) and the shared extension at `~/Claude/{project}/_booping/agent_booping-<name>.md`, injected at agent load time via `tools.render('src/templates/_partials/_extra_instructions.j2', extra_instruction_key='agent_booping-<name>')` in the agent template (owned by the `learn` playbook). A skill or playbook (e.g. `develop`) may also delegate to a **self-contained global agent** the project provides at `~/.claude/agents/<id>.md` — invoked by bare name through the Agent tool (`subagent_type="<id>"`), the same path the built-in workers use. Such an agent is wired in via a plain `core.{name}_playbook.agents.<id>` config block plus a `_booping/skill_<name>.md` extension that shapes its briefing. See [documentation/integrating-external-agents.md](documentation/integrating-external-agents.md).
- **Per-project quality checks**: the `develop` playbook's `verify` step runs the project's own lint / typecheck / test tooling, alongside plan-authored `Verify` commands. Command discovery order: repo `CLAUDE.md` → `_booping/skill_develop.md` → inspection of `package.json`, `pyproject.toml`, `Justfile`, etc.
- **Init flags**: `_project_context.j2` opens its yaml block with `booping_initialized` (a global config tier exists at `${XDG_CONFIG_HOME:-~/.config}/booping/config.yaml`, carried on `Context.booping_initialized`) and `project_initialized` (a `.booping` marker resolved). Both render on both branches — the no-project branch emits the block too. `booping config-get home_dir` always resolves (core default), so it answers *what* the home dir is, never *whether* booping is set up; that is `booping_initialized`'s job alone. The `setup` playbook's steps branch on these flags instead of discovering entry state.
- **Local vault**: `_project_context.j2` exposes `is_local_vault` (true when the resolved vault lives inside the repo working tree). Branch selection belongs to the `develop` playbook's `provision` step, not to grooming. The `setup` playbook prompts for vault location; `booping-create-project --local` scaffolds the repo-local variant.

## Config schema (`src/config.yaml`)

Two top-level keys: `home_dir` and `core`. **Placement rule** for everything under `core`: a key exactly one playbook owns lives at `core.{name}_playbook` (the playbook name with `-` → `_`); a key the development loop or several playbooks share lives directly under `core`. Nothing is validated — these are the keys the shipped playbook set reads, not a closed schema.

### Top level

- `home_dir` — vault-home base for `<home_dir>/<project>/`, a raw string (`~` expanded at vault-resolution time). Resolved from the core+global partial merge **before** the project tier, so setting it in the project tier is a no-op; a `.booping` `vault_path:` marker still wins over it. Top-level because it resolves the vault before any namespace is reachable.

### Shared, directly under `core`

- `core.research_agent` — the agent id a playbook step delegates its bulk reads to when it is **assisted** (default `booping:booping-researcher`); rendered as `{{ config.core.research_agent }}` by the step bodies that delegate and by `_playbook_driving.j2`.
- `core.macros.<name>` — an argv list (never a shell string) a rendered body calls by dotted path via the `macro()` global: `{{ macro('core.macros.date', '+%H:%M') }}`. Run with `shell=False`; stdout stripped and cached per argv tuple for the process, so a declared macro must be idempotent within one render. The declared list is an argv **prefix**: extra positional arguments at the call site append to it, so `["date", "+%Y%m%d-%H-%M"]` (complete) and `["date"]` (partial) are the same shape — there is no opt-in key. Distinct arguments are distinct argv tuples and therefore distinct runs, so two formats of the same clock can disagree across a minute boundary. The core tier declares one macro, `date: ["date"]`. Honoured in **every** tier, project included — no tier drops it any more; the accepted consequence is that a repo carrying a local vault can declare argv a render executes. `--stub-macro <key>=<literal>` (on `render`, `render-playbook` and `scaffold`) returns the literal without executing; that is what makes a committed report byte-reproducible. The key is either the dotted path plus the call's arguments (`core.macros.date +%H:%M`), pinning that one call, or the path alone, pinning every argument variant — **the specific key wins**. Pairs split on the first `=`, so an argument containing one cannot be pinned.
- `core.plans.glob` — plan shape as data: the single entry `plans/*/index.md`. A plan is a directory claimed by its `index.md`; a vault with a different shape edits this one key. The engine still honours list order (first glob to claim a slug wins) for a vault that declares several. It is also the fallback every query spec without its own `glob` inherits (`query.DEFAULT_GLOB_PATH`).
- `core.task_types` — list of `{type, description, doc_uri}`. Rendered by `playbooks/_partials/task_types.md` as a table with a lazy-load link to `doc_uri` (relative from repo root); the partial reads `config.core.task_types` unless the caller sets a `task_types` variable.
- `core.sprint` — `scale` (list of `{sp, meaning}`), `default_threshold_sp` (SP total past which `groom` should propose splitting — not a velocity), `redecompose_threshold` (tasks ≥ this SP must be re-decomposed), `max_milestones_per_agent` (consecutive milestones `develop` may group into one briefing). Rendered by `playbooks/_partials/sprint_planning.md`; falsy thresholds are skipped.

### Per-playbook, under `core.{name}_playbook`

- `core.groom_playbook` — `cross_review_agent`, `agents`, `queries.latest_plans`. `cross_review_agent` is the agent id that performs a detached second-model review of a drafted plan, **core default `null`**. It is read only by the `cross-review` step, which gates all three of `summary`, `detached:` and body on it — the preamble carries no cross-review block, so the step owns the whole surface. `detached:` renders `{{ config.core.groom_playbook.cross_review_agent or '' }}` (the `or ''` matters: a bare `null` renders the string `None` and would be taken for an agent id); without an agent the summary renders as skipped, so the runner sees the skip in the step table rather than inheriting a review body it would perform itself.
- `core.develop_playbook` — `git`, `agents`. `git.commit_message` is the conventional-commit format string; `git.branches` is a list of `{branch, when}` entries where `branch` is the literal prefix string (slash and format up to the user, e.g. `feat/`) and `when` a list of short matches (plan `type` names like `feature`, or freeform descriptors). Rendered via the `playbooks/_partials/_git_guide.j2` macro; consumed by the `provision` step for branch selection.
- `core.retro_playbook` — `status`, `queries.candidates`, `agents`.
- `core.learn_playbook` — `status`, `queries.candidates`.
- `core.code_review_playbook` — `status`, `queries.review_candidates` (the `/code-review` skill's argument-free plan picker), `queries.scope_candidates` (the `code-review` playbook's `scope` step, which also needs the diff base), `agents`.
- `core.migrate_playbook.queries.pending` — the query spec over the migrations the plugin ships (below).
- `core.setup_playbook.scaffold`, `core.playbook_authoring_playbook.scaffold` — the two scaffold trees (below). The rule is applied literally here too: verbosity is the price of the convention being teachable.

Shapes shared across those blocks:

- `agents.<agent-name>.good_for` / `.bad_for` — delegation guidance rendered by `playbooks/_partials/playbook_agents.md`, which a playbook body invokes by setting `playbook_agents` to its own `core.{name}_playbook` block. It is the **only** delegation-table surface; both `available_agents` partials are gone. The `code-review` **skill** renders an equivalent table inline against `core.code_review_playbook`, because the skill render env's loader is rooted at `src/templates/` and cannot reach `playbooks/`.
- `agents.<agent-name>.internal` (true on built-in entries) and `disable_internal_agents` — when `disable_internal_agents` is set on the block, the table hides booping's built-in (`internal: true`) agents, leaving only the agents the project explicitly registered (e.g. a self-contained global external agent). See [documentation/integrating-external-agents.md](documentation/integrating-external-agents.md).
- `status` — the single plan status this playbook claims from or reads. `learn` reads `awaiting-learning`; `retro` and `code-review` read `awaiting-retro`. Rendered into bodies that gate on or query one status. It is a query key, not a lifecycle definition — the transitions live in the playbook's `states:`.
- `queries.<id>` — a query spec (below), living beside its consumer.

### Query specs

- **Query spec** — any mapping in the merged config, addressed by its dotted path (`booping query --config <dotted.path>`, `{{ '<dotted.path>' | query }}`); the value at the path **is** the spec, no wrapper key, exactly like `config-get` and `scaffold`. All keys optional: `glob` (ordered patterns, first to claim a slug wins — slug is the parent dir name when the pattern's last segment is a literal filename, else the file stem; omitted → `core.plans.glob`), `root` (what the globs resolve against: omitted → the vault, `core` → the plugin root, for content the plugin itself ships — a `root: core` spec therefore resolves outside any project), `where` (clause → value, operator carried as a key suffix: `k` equality, `k!` inequality, `k:in` membership, `k:gt` / `k:lt` numeric ordering — both operands coerce with `float()`, and a side that will not coerce fails the clause, exactly as a row missing the field does), `sort` (frontmatter field, `-` prefix descending; valueless rows last; omitted → slug order), `columns` (projection, declared order kept; `path` and `slug` always present). Extra keys are forbidden, so a misspelled `root` (or any other typo) is an error naming the legal set rather than a silent fallback. A spec lives beside its consumer (`core.{name}_playbook.queries.<id>`), never in a central registry. Inline arguments (`--where`, `| query(where={...})`) deep-merge over it for that call only. Rows are attribute-accessible `Row` objects, never dicts — Jinja resolves `foo.bar` as `getattr` first, so a frontmatter key named `items` / `keys` / `get` on a plain dict would render a bound method.
- `core.migrate_playbook.queries.pending` — the query spec over the migrations the plugin ships: `root: core`, `glob: migrations/*/migration.md`, `sort: id`. Despite the name it lists **all** of them; the `migrate` playbook narrows it to the genuinely pending set with `where={'id:gt': booping.latest_migration}`. The `booping` render global (available in `render`, `render-playbook` and `scaffold` seed content) carries `latest_migration`, read off the resolved `.booping` marker: a **watermark**, so `7` means everything at or below 7 is done and a migration numbered 5 merged afterwards never runs; `-1` when nothing has been applied (key absent) or no project is attached, while a non-integer value is a load-time error naming the marker. The gate that consults the same watermark is deliberately more forgiving — `migrations.recorded_id` treats anything unreadable as behind, so a corrupt marker yields the remedy rather than a stack trace.

### Scaffold trees

Any mapping in the merged config can be a **scaffold tree** — a declarative file/dir structure `bin/booping scaffold <dotted.path> <dest>` materialises. Trees have no wrapper key: the value at the addressed path **is** the root directory's contents. They ride the ordinary core → global → project deep merge, so a global or project config can add a tree or override a single leaf of a core one. Node encoding (parsed by `booping.context.scaffold`):

| Config value | Meaning |
|---|---|
| string | File; the string is its content, Jinja-rendered |
| mapping without `type` | Directory; entries are its children (key = filename) |
| `{type: file}` | File; optional `content` (absent → empty file) |
| `{type: dir}` | Directory; optional `children` (absent → empty dir) |
| `null` | Error — use `""` for an empty file, `{}` for an empty dir |
| list, number, bool, any other scalar | Error, reported against the node's dotted path |

`type` is a **reserved key** inside a tree: a mapping carrying it is an explicit node descriptor, never a directory named `type`. (`content` / `children` are the only other keys an explicit node accepts; `mode` is deliberately unimplemented, the reserved key keeping the escape hatch open.) A filename key containing `/`, or equal to `.` or `..`, is rejected before any write. Seed content renders through `rendering.build_source_env`, so `{{ config.… }}` / `{{ context.… }}` resolve, and `--set key=value` binds a **bare** variable (`{{ name }}`) — unlike `render` / `render-playbook`, where `--set` merges into `config` (`{{ config.name }}`).

- `core.playbook_authoring_playbook.scaffold` — the playbook skeleton the `playbook-authoring` playbook materialises: `playbook.md` with identity frontmatter, `playbook.yaml` with an empty `graph:`, an empty `_references/`. Seeded with `--set name=<playbook-name>`.
- `core.setup_playbook.scaffold` — the project-vault tree the `setup` playbook materialises: `plans/`, `retrospectives/`, `_lessons/`, `_booping/`, `notes/` plus `sprints.md` (an Obsidian Bases fence over `plans/`) and a `.gitignore`. Takes no `--set` variables.

## Plan lifecycle

There is no shared lifecycle any more — `config.plan`, the `transition` and `vault-commit` commands and the `plan_status:` frontmatter mirror are all deleted. **Each playbook owns its own status vocabulary** in its `playbooks/<name>/playbook.yaml` `states:` block, and `booping playbook-transition` is the only writer.

- The plan directory `plans/{slug}/` is the run workdir for the playbook operating on it, and `index.md` is both the run artifact and the plan document. A plan's `status:` is therefore whatever the running playbook's machine last wrote.
- The shipped playbooks chain their machines through the plan: `groom` (`framing` → `researching` → `drafting` → `cross-reviewing` → `presenting` → `awaiting-approval` → `ready-for-dev`), `develop` (`awaiting-plan-review` → `ready-for-dev` → `in-progress` → `awaiting-retro` | `fail`), `retro` (`awaiting-retro` → `awaiting-learning`), `learn` (`awaiting-learning` → `done`). `groom` and `develop` also reach the terminal `cancelled` from every non-terminal status, declared once per superstate rather than per status. `code-review` is stateless. The chaining is a convention between the playbooks, not an engine feature — read the `states:` block for the authoritative set.
- A vault commit is a playbook's own business: `groom` fires `script commit-plan` on its superstate-boundary edges, `retro` / `learn` fire `script close-working-set`, and `retro`'s `_scripts/drop-plan {slug}` marks a skipped sibling done. `playbooks/<name>/_scripts/` is where each lives.
- Plans carry an optional `commit:` frontmatter field (repo HEAD at the time of the snapshot), stamped by a `frontmatter-update commit=@head` hook on `develop`'s `ready-for-dev → in-progress` edge. Plans without `commit:` load with `commit: None`.
- `sprints.md` is an **Obsidian Bases fence** seeded once by `core.setup_playbook.scaffold` and written by nothing thereafter — Obsidian evaluates it live, so it never goes stale and never needs a re-render hook. It is purely human-facing: no skill, playbook body or command parses it, and the machine-facing listing is `booping query`. Outside Obsidian it is an inert code block.

See [documentation/playbook.md](documentation/playbook.md) for the run-state mechanics (`states:`, hooks, workdir, resume).

## Project vault layout (`~/Claude/{project}/`)

- The vault lives at `~/Claude/{project}/` by default, or at a repo-local directory when the `.booping` marker carries an optional `vault_path:` key (relative paths resolve against the repo root; absolute paths and `~` expansion are honoured; absent → `~/Claude/{project}`). `booping-create-project --local [dir]` (default `./booping`) scaffolds the local variant and writes both `vault_path:` and a vault `.gitignore`.
- The vault is **Obsidian-ready**: markdown files + YAML frontmatter that Obsidian renders as Properties. No proprietary database. Open the vault directory in Obsidian for graph view + backlinks across plans, retros, and lessons.
- `plans/{YYYYMMDD}-{kebab-title}/index.md` — **a plan is a directory** (what the `groom` playbook writes, the directory doubling as its run workdir), carrying its body and frontmatter (per `docs/template_plan_frontmatter.md`) in `index.md`; the directory name is the slug. Sibling stubs set `split_from: plans/...` to point at the primary plan they were split from. The shape is the `core.plans.glob` config key rather than engine logic — one entry, `plans/*/index.md`. A file whose frontmatter can't be parsed is skipped with a stderr warning, never a crash.
- `plan_templates/*.md` — project-local plan templates. Each has frontmatter (`name`, `description`) + two top-level sections (`# Plan Body`, `# Quality Checklist`). Discovered alongside core templates by `PlanTemplate.load_all()`; can override a core template by sharing its `name`, or add entirely new ones.
- `review_templates/*.md` — project-local code-review templates. Loaded by `/code-review` alongside core templates under `docs/review_templates/`; selected per-plan based on stack signals.
- `lessons/` — legacy accumulated lessons; loaded by `Lesson.load_all` → `context.lessons` and still read by `_lessons.j2` (the `code-review` skill, the researcher agent, and the groom / retro / code-review playbook steps that include it). Nothing writes it any more — the `learn` playbook writes `_lessons/`.
- `_lessons/` — targeted lessons, each carrying a `targets:` list (`{playbook}`, `{playbook}/{step}`, `agent:{id}`); loaded by `Lesson.load_targeted` → `context.targeted_lessons`, shadowing same-named files in the machine-wide `<home_dir>/_lessons/`. Written by the core `learn` playbook; injected by `render-playbook` and by the internal agent bodies.
- `notes/` — user notes (plan-review comments, code-review threads, ideas for next sprints). Not consumed by skills or agents — purely for the user's own reference.
- `_booping/skill_<name>.md` — project-local extensions to wide-domain skills.
- `sprints.md` — an Obsidian Bases fence over `plans/`, seeded once by `core.setup_playbook.scaffold` and rewritten by nothing. The user's to edit.
- `_booping/.booping.log` — append-only invocation log. `render`, `render-playbook`, `query`, `scaffold`, `marker-set`, `frontmatter-update`, `playbook-state` and `playbook-transition` write one line per call. Format: `<iso8601-utc>: [<subcommand>] <detail>`.

(Project conventions live in the attached repo's own `CLAUDE.md`, not in the vault.)

## CLI

- `bin/booping render <template-path> [--output <path>] [--set <key>=<value>] [--stub-macro <path>=<literal>]` — render a Jinja2 template with full project context to stdout (or to a file with `--output`). Used at skill-load time via `!`booping render ...`` and to render a shared playbook partial from the command line. Gated on migrations: when the marker's `latest_migration` is below the highest id the plugin ships, the normal output is replaced wholesale by a `**STOP — tell the user:**` notice pointing at `/playbook migrate`, at exit 0 with stderr empty. `--set <dotted.key>=<value>` carries the same semantics as on `render-playbook` (repeatable, later pairs win, values stay strings, final tier over core → global → project, a pair without `=` → stderr + exit 1) — how a shared partial is parameterised from the command line (e.g. `booping render playbooks/_partials/lesson_target_space.md --set targets_for=groom,learn`).
- `bin/booping query [--config <dotted.path>] [--glob <pattern>]... [--where <K=V>]... [--sort <field>] [--columns <a,b>] [--output <format>] [--project <path>]` — list vault markdown files by frontmatter. `--config` addresses a query spec in the merged config; `--glob` is the ad-hoc form (repeatable, ordered) — exactly one of the two. `--where` is a fixed operator vocabulary, not an expression language: `k=v`, `k!=v`, `k:in=a,b`, `k:gt=n`, `k:lt=n` (repeatable, all clauses apply; a row missing the field fails every operator). `:gt` / `:lt` are **numeric**: both operands coerce with `float()` and a side that will not coerce fails the clause, same as a missing field. `--sort <field>` (`-` prefix descending) over the deterministic slug base order; `--columns` projects, declared order preserved. `--output` is `table` (default), `json`, `yaml` or `paths`. A spec declaring `root: core` globs the plugin root and so needs no vault; without it a vault must resolve. Exit 0 including zero rows; 1 on user error (malformed `--where`, unknown `--config` path, non-mapping value there, unknown `root` value or any other rejected spec key, both or neither of `--config`/`--glob`, unknown `--output`); 2 on an unreadable or unresolvable vault. Logs to `.booping.log`.
- `bin/booping render-playbook <name> [--step <step>] [--project <path>] [--output <path>] [--no-lessons] [--inline-steps] [--set <key>=<value>] [--stub-macro <path>=<literal>]` — render a playbook's composed procedure to stdout (or a file with `--output -`/`PATH`): notices + preamble + `## Lessons` (lessons targeting the playbook by name, when any) + `## Playbook Steps` (a step table — step, dependencies, summary, review gate — in dependency order) + wave-ordered step sections. `--step <step>` prints that one step's body alone (no headings, instruction bullets, or gate chrome), followed by a `## Lessons` block of the lessons targeting `{playbook}/{step}` — the fetch path composed sections point at for later waves of a `jinja: true` playbook; unknown step → stderr + exit 1. `--no-lessons` drops lesson injection **and** the lesson notices on both surfaces (byte-identical to a lesson-free vault; used by the eval harness). `--inline-steps` embeds each runner-performed step's rendered body in its section instead of the fetch line (detached steps unaffected); implied by `inline_steps: true` in the manifest frontmatter. `--project <path>` resolves context against that vault instead of the attached project (also satisfies `requires_project`) — used for rendering/eval outside a project; it additionally **pins discovery to core + that vault** for both playbooks and targeted lessons, skipping the machine-local global roots (`<home_dir>/_playbooks/`, `<home_dir>/_lessons/`), which is what makes a committed report reproducible on another machine. It also resolves the `.booping` marker from that root rather than from cwd, pinning `booping.latest_migration` (and so the migration gate) to the fixture's watermark — `playbooks/_fixtures/vault/.booping` carries it, and it must be bumped when a new migration ships or `just playbook-reports` will churn. The migration gate applies exactly as on `render` (the STOP notice replaces all output at exit 0), with one exemption keyed on the requested name: `migrate` never traverses its own gate, because it is the remedy. `--set <dotted.key>=<value>` overrides one config value for this render only: repeatable (later pairs win), the parsed mapping deep-merges as the final tier over core → global → project, values stay strings, and a pair without `=` → stderr + exit 1. `--stub-macro <key>=<literal>` (repeatable) makes a macro return the literal without executing — the key is the dotted path, optionally followed by the call's arguments (`core.macros.date +%Y%m%d%H%M`), the argument-qualified key winning over the bare path. That is what makes a committed report byte-reproducible. Unknown playbook → stderr + exit 1; graph problems → in-band STOP/Note notices (exit 0). Logs to `.booping.log`. A states-bearing playbook additionally renders a `## State` section after the execution graph.
- `bin/booping playbook-state <playbook> [--workdir <path>]` — read-only run frontier as YAML: playbook, resolved workdir, and per `states:` entry its `artifact`, current `status` and `next:` edges (`to` + declared `when`/`gates`); per-instance entries report an `instances:` mapping keyed by slug (globbed off disk); a missing artifact reports `status: not-started` with a bootstrap edge to `initial`. Workdir defaults to cwd. Unknown playbook / missing workdir / no `states:` / artifact without `status:` → stderr + exit 1. Logs to `.booping.log`.
- `bin/booping playbook-transition <playbook> <to> [--state <name>] [--instance <slug>] [--workdir <path>]` — the only writer of playbook run state: resolves the state machine (`--state` defaults to the outer `state:` ref; `--instance` required iff the artifact path carries `{instance}`), checks `<to>` is reachable from the artifact's current status, sets `status: <to>` and runs the edge's hooks (`frontmatter-update`, `script`) in order. A missing artifact is bootstrapped (legal only when `<to>` is `initial`); re-running the same target is idempotent. Prints the authoritative mutation report. Illegal transition/unknown state → exit 1; hook failure → exit 2. Logs to `.booping.log`.
- `bin/booping config-get <dotted.key>` — print a single resolved config value across the core → global → project merge (e.g. `home_dir`, `core.sprint.default_threshold_sp`, `core.task_types`). Scalars print as raw text (one line, no quotes; `home_dir` prints its raw unexpanded value); mappings/lists print as YAML. Works outside any project (core + global only). Missing key → stderr + exit 1; unreadable config → exit 2. Used by `bin/booping-create-project` to resolve the vault-home base.
- `bin/booping marker-set <key>=<value>` — set one key on the `.booping` marker resolved by walking up from cwd. Exactly one pair; `latest_migration` is the only key with meaning today (its value is validated as an integer, or the literal `@latest`, which resolves to the highest id under `migrations/` — what `bin/booping-create-project` writes so a fresh project starts current), but the command takes an arbitrary key so the marker stays writable as it grows. The value is set **absolutely, never incremented** — it is a watermark, so ids may skip. stdin is not read and stdout stays empty; the single authoritative line goes to stderr (`marker: latest_migration=3`). Exit 0 on success; 1 on user error (pair without `=`, empty key, non-integer `latest_migration`); 2 on environment failure (no marker resolvable from cwd, a marker that is not a YAML mapping, `OSError` mid-write). Writes through `update_marker()` in `context/_yaml.py` — a ruamel round-trip that preserves comments and key order; the marker is a bare YAML mapping, so `update_frontmatter` would prepend a `---` block and produce a two-document stream. Logs to `.booping.log`.
- `bin/booping scaffold <config-path> <dest> [--force] [--set <key>=<value>] [--stub-macro <path>=<literal>]` — materialise a config-declared file/dir tree into a destination directory. `<config-path>` is a dotted path into the merged config addressing the tree (e.g. `core.playbook_authoring_playbook.scaffold`); `<dest>` is the destination, created with parents when missing. A non-empty destination aborts unless `--force`, which overwrites only the files the tree names and never deletes a directory. Seed content is Jinja-rendered through `rendering.build_source_env` (so `config` / `context` globals resolve); `--set <key>=<value>` binds **bare template variables** (`--set name=x` fills `{{ name }}`) — a deliberate divergence from `render` / `render-playbook`, where `--set` deep-merges into `config` and is read as `{{ config.name }}`; repeatable, later pairs win, values stay strings. The whole tree is parsed and rendered in memory before the first write, so a malformed node or Jinja error leaves the filesystem untouched. stdout carries one `created dir <path>` / `created file <path>` / `overwrote file <path>` line per path plus a totals line. Exit 0 on success; exit 1 on user error (unknown config path, non-tree value, invalid node, `null` node, unsafe filename key, non-empty destination without `--force`, malformed `--set`, Jinja error in seed content); exit 2 on `OSError` mid-write. Logs to `.booping.log`. Core trees today: `core.playbook_authoring_playbook.scaffold` (playbook skeleton — `playbook.md`, `playbook.yaml`, `_references/`) and `core.setup_playbook.scaffold` (project-vault tree, including the seeded `sprints.md` Bases fence).
- `bin/booping frontmatter-update <plan> [key=val ...] [--remove <key>...]` — set or remove plan frontmatter keys. A value is **Jinja-rendered with the `macro` global** — `planned="{{ macro('core.macros.date', '+%Y-%m-%d %H:%M') }}"` — so the clock is the one config-declared `core.macros.date` macro rendered bodies already call, the format lives at the call site, and `--stub-macro` pins it exactly as it pins a render (a transition is reproducible the same way). A value carrying no Jinja passes through untouched; a macro or Jinja error exits non-zero with the offending value on stderr. The one surviving token is `@head` (repo HEAD sha) — deliberately not a macro, because it must resolve against the repo directory while a macro runs in the process cwd (the run workdir during a playbook transition). `--remove <key>` (repeatable) drops keys; removals apply before `key=val` sets. The atomic primitive the `frontmatter-update` playbook hook is built on.
- `bin/booping build` — render every `src/files/**/*.j2` to its plugin-root destination using `src/config_files.yaml`. Run after editing any `src/files/<rel>.j2` or `src/config_files.yaml`.
- `bin/booping debug-context` — dump the assembled `Context` as YAML for troubleshooting.
- `bin/booping debug-template <template-path>` — render a template and append a debug context footer.
- `bin/booping-create-project <project-name> [--local [dir]]` — scaffold the vault directories + `.booping` marker. In default mode the vault-home base is resolved via a ladder: global `home_dir` (when `${XDG_CONFIG_HOME:-~/.config}/booping/config.yaml` exists, read through `config-get`) → `$HOME/Claude` if it exists → interactive prompt (default `~/Claude`) whose answer is seeded into the global config file (never clobbering an existing one); non-interactive with none satisfied aborts. The vault then lands at `<home_dir>/{project}/`. `--local [dir]` (default `./booping`) scaffolds a repo-local vault instead, writing a `vault_path:` key into `.booping` plus a vault `.gitignore`. Both branches finish with `booping marker-set latest_migration=@latest`, so a vault created against today's plugin never reports itself behind.
- `bin/booping-external-llm-call --prompt=<name> --context.<key>=<path>... [-- <free-text>]` — render a Jinja2 prompt template from `bin/llm-call-templates/<name>.md.j2` and send it to Gemini. Handles its own API-key check. Current templates: `validate-plan`.
- `just build` — one-shot build via `bin/booping build`. `just dev` watches `src/files/` + `src/config_files.yaml` and rebuilds on change (requires `watchexec`).
- `just lint`, `just typecheck`, `just test` — run ruff, basedpyright, pytest against `booping-python/`.
- `just playbook-reports [which]` — the **committed** reports: render every `playbooks/<name>/playbook.md` against the fixture vault (`--project playbooks/_fixtures/vault` plus one `--stub-macro` per timestamp format the playbooks call) into `playbooks/<name>/_reports/output.md`. `which` narrows to one playbook (`just playbook-reports groom`). Any non-zero render fails the recipe, and so does a `**STOP` notice in any output — graph and Jinja problems are in-band at exit 0, so without that guard a broken playbook would report success.
- `just playbook-reports-live [which]` — the **debug** render: the attached project's own vault, no `--project`, macros executed for real, into `playbooks/<name>/_reports/local.md` (gitignored). Surfacing STOP notices is the point, so they print instead of failing. This is the mode that catches a macro or query error the committed run's stubs hide.

## Editing conventions

- Edits to `src/templates/skills/*.md.j2`, `src/templates/agents/*.md.j2`, and `src/templates/_partials/*.j2` are **live** — rendered at skill-load time, no rebuild needed.
- Edits to `src/files/**/*.j2` or `src/config_files.yaml` require `just build` to materialize into the on-disk `skills/<name>/SKILL.md` / `agents/<name>.md`. `git diff -- skills/ agents/` after `just build` is the drift signal.
- `skills/<name>/SKILL.md` (today `code-review` and `playbook`) and `agents/<name>.md` are **build artefacts** — never hand-edit. Edit `src/files/<rel>.j2` (or `src/config_files.yaml` for shared frontmatter values) and run `just build`.
- Edits to playbook sources — manifests (`playbook.md` / `playbook.yaml`), step `prompt.md` bodies, and any shared partial they include — require `just playbook-reports` to refresh the committed reports. `git diff -- playbooks/*/_reports/` after the run is the drift signal; a shared partial makes it span several playbooks.
- `docs/*.md` is hand-authored. No build step regenerates it.
- `documentation/*.md` is hand-authored. Only `mkdocs build` consumes it, and the build runs in GitHub Actions on push to `main` (`.github/workflows/docs.yml`) — there is no local-build-on-commit step. Use `just docs` / `just docs-serve` for local preview.
- Prefer extracting to a partial over inlining when prose grows past a paragraph or two.
- Prefer moving structured data into `src/config.yaml` over prose in partials.
- No comments that restate code. Only WHY for non-obvious bits.
- Conventional commits with scope: `feat(booping): ...`, `fix(install): ...`, etc.
- The plugin code itself stays stack-agnostic — no Python/Django/JS specifics inside skills.
- README.md's Statuses section is hand-maintained narrative over the per-playbook status vocabularies — revisit it whenever a playbook's `states:` block changes (status name, meaning, terminal flag, or addition/removal).

## Adding a new template-driven skill

Most new procedures should be a **playbook**, not a skill — a skill is for a surface `/playbook` cannot drive. Use `src/templates/skills/code-review.md.j2` as the reference.

1. Decide what goes in config vs prose: structured values (agents, the status it reads, query specs) belong in `src/config.yaml` under `core.{name}_playbook`; verbs, heuristics, and judgment calls go in the template.
2. Author the template at `src/templates/skills/<name>.md.j2`. No frontmatter — the thin shell carries it. Standard wiring:
   - `{% include "_partials/_project_context.j2" %}` — loads project name/path at render time.
   - `{{ tools.render('src/templates/_partials/_lessons.j2') }}` — inlines live lessons.
   - `{{ tools.render('src/templates/_partials/_extra_instructions.j2', extra_instruction_key='skill_<name>') }}` — inlines project-local skill extension.
   - A delegation table, **inlined**: the skill env's loader is rooted at `src/templates/` and cannot reach `playbooks/_partials/playbook_agents.md`. Copy the block from `code-review.md.j2` and point it at your `core.{name}_playbook` config block.
3. Add the `agents` block (and any `status` it reads, plus its query specs) to `src/config.yaml` under `core.{name}_playbook`.
4. For any detail only some routes need, write it as `docs/<name>.md` and lazy-link from the skill body with `[label](${CLAUDE_PLUGIN_ROOT}/docs/<name>.md)` rather than inlining.
5. **Author** `src/files/skills/<name>/SKILL.md.j2` as a thin shell: copy frontmatter shape from a sibling (e.g. `src/files/skills/code-review/SKILL.md.j2`); set `allowed-tools` (include `Bash(booping:*)` plus any non-booping shell calls the skill needs); use `effort: {{ skills.<name>.effort }}` and add the matching key to `src/config_files.yaml` under `skills:`; set the body to `!`booping render src/templates/skills/<name>.md.j2``.
6. Run `just build` to materialize `skills/<name>/SKILL.md`. Sanity-check by running `bin/booping render src/templates/skills/<name>.md.j2` and inspecting the output.
