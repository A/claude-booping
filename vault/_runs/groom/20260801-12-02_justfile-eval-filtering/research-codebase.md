## Prior art

- `bin/eval-md.sh` + `justfile:35-36` — the established split: the recipe stays a one-liner (`@bin/eval-md.sh {{ args }}`) and all logic lives in a `bin/*.sh` opening with `set -uo pipefail` and `here=$(cd -- "$(dirname -- "${BASH_SOURCE[0]}")" && pwd)`. Precedent for where a selector resolver goes and how it is invoked.
- `bin/booping` — shell wrapper that resolves the plugin root from its own location rather than the caller's cwd. Precedent for making a `bin/` script's path handling independent of where `just` was run.
- `justfile:28-46` — `[no-exit-message]` plus a single `*args` variadic on every eval recipe. Precedent for the arg contract the selector extends; verified with `just 1.57.0` that `-`-leading arguments after a recipe name reach the recipe verbatim, so a leading non-`-` positional can be recognised as the selector without colliding with promptfoo flags.
- `bin/report-md.jq` — jq rendering driven off one promptfoo `--output` JSON, keyed on `.config.description` for the report title. Precedent for report shape and the constraint a multi-suite run has to satisfy.
- `playbooks/groom/*/promptfooconfig.yaml` — eight structurally identical suites (`description: groom <step>`, one `prompts:` entry, one provider with `mode: step` / `output_mode: files`, `defaultTest: file://../../_lib/grader.yaml`, `tests: file://tests.yaml`). Precedent that a suite is fully identified by its directory path, so the selector needs no config parsing.
- `playbooks/groom/*/tests.yaml` — every case carries `metadata: {playbook, step, tier}`, and `--filter-metadata` is repeatable with AND logic. Precedent for a second, already-present filter axis (`--filter-metadata tier=regress --filter-metadata step=design`) that the design can weigh against path resolution.

## Conventions in play

- A `just` recipe stays a one-liner; anything with branching lives in a script the repo can read and run without going through `just` — demonstrated by `justfile:35-36` → `bin/eval-md.sh`. Selector logic therefore belongs in `bin/`, not inline in the recipe body.
- Every eval recipe carries `[no-exit-message]` (`justfile:29,34,39,44`) so a failing suite does not add just's own error banner on top of promptfoo's. Any new or reshaped recipe keeps it.
- `_`-prefixed directories are workspace, not playbooks or steps (CLAUDE.md's playbook-loader rule: `_`-prefixed dirs skipped; `_references/`, `_fixtures/` free workspace). Discovery must apply the same rule rather than trusting glob depth.
- The justfile is hand-authored and outside the `src/files/` build pipeline — this work triggers no `just build` and produces no build-artefact drift in `skills/` or `agents/` (CLAUDE.md editing conventions).
- Quality gates are `just lint` / `just typecheck` / `just test`, all scoped to `booping-python/` (CLAUDE.md:176), and `.github/workflows/ci.yml` never invokes promptfoo. A new `bin/*.sh` ships with no automated coverage; verification is manual invocation.
- CLAUDE.md is the ownership map and currently states the eval harness is *not* in this repo (line 36) while the CLI section (line 176) omits the eval recipes entirely. A documented selector grammar has to land in one of those two places or the repo keeps contradicting itself.
- Conventional commits with scope (`feat(booping): …`) per CLAUDE.md editing conventions.

## Unknowns for design

- **Multi-suite execution shape.** promptfoo's variadic `-c` merges configs — `combineConfigs` dedupes `providers` into one list and concatenates every config's `tests` — so a `groom/` or bare selector run as a single process would grade each step's fixtures against every other step's prompt and model. Design must commit to N sequential promptfoo processes and decide what the aggregate then is: per-suite output only, or a totals line and a rolled-up exit code (any failure → 1).
- **`eval-md` under a multi-suite selector.** `bin/eval-md.sh` renders one temp JSON through `report-md.jq` into one `glow` view. Choose: one report and one glow per suite, one concatenated markdown across suites, or `eval-md` accepting only single-step selectors.
- **Substring ambiguity.** Confirmed matching is substring, so `groom/de` hits both `decompose-work` and `design` and `groom/o` hits five. Decide whether every match runs (consistent with the confirmed zero-match no-op) or whether a multi-hit selector is itself an error — the two rules pull in opposite directions.
- **Cost of the bare invocation.** `just regress` with no selector becomes 8 suites × 4–6 judged cases, each with opus judge calls, in one command. Decide whether that stays a silent full sweep or gets an up-front count/confirmation.
- **Resolver decomposition.** One script behind all four recipes (`bin/eval-run.sh <tier|-> [selector] [args…]`) versus a path-emitting helper the recipes consume — and whether to port the out-of-repo vault harness at `~/Claude/_playbooks/_scripts/sweep.sh` (per-suite loop, `SWEEP_PROGRESS_FILE` ticker the committed provider already feeds, `report.jq` per-suite lines, totals) or write a minimal repo-local resolver.
- **Zero-match must not fall through.** Called with no `-c`, promptfoo auto-loads `./promptfooconfig.yaml`, which does not exist at the repo root, so it errors. The confirmed silent-no-op path has to short-circuit before any promptfoo invocation rather than emit an empty config list.
- **Composition with an explicit `-c`.** Callers can still pass `-c playbooks/groom/intake/promptfooconfig.yaml` alongside a selector. Decide whether the selector wins, the flag wins, or the combination is rejected.
