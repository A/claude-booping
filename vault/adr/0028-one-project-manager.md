## Context

Two user-level playbooks do overlapping work: `orchestrate` (a live session where the
user gives requests and the agent grooms, develops, reviews, merges and reports) and
`backlog-run` (a nightly run over cross-project backlog tasks with a state machine,
budget gates and pause/resume). A study of six orchestrator sessions (2026-09-27 to
10-08) found requests arriving 3-5 per message with up to six tracks in flight, and
state spread over the board, a handoff file, `epics.md`, `backlog.md`, memory and
compaction summaries: finished runs sat unnoticed for 15 hours, board statuses went
stale, questions asked only in chat were lost, and the owner asked for status again
and again. The owner settled the shape on 2026-10-15.

## Decision

A core playbook `project-manager` is the manager the user talks to; it manages the
leads — groom and develop — and works in the project's autonomy mode
([adr/0027](0027-autonomy-modes.md)).

- **One item store.** Work is items in the vault (the open items of
  [adr/0025](0025-open-items-are-an-index.md)), with a source: a user request (the
  user's words verbatim), a spec gap, a backlog task. Every user message is split into
  items as it arrives, asides included. Ideas and decisions stay in specs as `idea`
  and `adr` records; an open idea nobody took is visible to the manager.
- **Status is computed.** "What is going on" is generated by code from items, open
  ideas, plans, runs, unreviewed records and marks — a short summary by default,
  detail on request. No stored handoff: a month later it cannot be stale, because it
  does not exist as a file.
- **Questions live on the item** (a sidecar); chat only points to the item.
- **Runs are registered.** Every launched run is recorded with its item and a
  fallback check, and a finished run surfaces on the next turn.
- **Autonomous mode** carries over backlog-run's size-based batching. It carries no budget or window gate, no pause and no resume, and nothing in the core starts it on a timer or an event ([value/0017](../value/0017-launching-and-guarding-runs-is-userland.md)).
- **Not core: usage limits.** Booping is the orchestrator of development — specs, plans, the roadmap and sprints. Guarding the subscription's usage limits, time windows for runs and pause/resume around them are not its problem: it never stops a user from spending their limits, and a user who wants a guard builds it on top (owner, 2026-10-17).
- **Not core:** intake from other channels (a messenger, a phone, ntfy) and merging
  duplicates, and tracker integrations (GitHub, GitLab, Linear, Multica …) — project or
  global rules and playbooks on top of `booping items add` and the item store.
  Project specifics such as a board's labels or a release procedure are project rules
  with `targets: [project-manager]` and project runbooks.

## Alternatives

| Option | Status | Complexity | Reversibility | Verdict |
|---|---|---|---|---|
| [One core project-manager](#one-core-project-manager) | accepted | high | medium | One pipeline, one state store |
| [Keep orchestrate and backlog-run](#keep-orchestrate-and-backlog-run) | rejected | low | high | Two copies of the pipeline, scattered state |

### One core project-manager

Both user playbooks fold into one core playbook over one item store.

- **Pros:** one place for status; computed handoff; one pipeline to improve; any
  project gets it.
- **Cons:** a large change; project specifics must be rewritten as rules.
- **Complexity:** high.
- **Reversibility:** medium.

### Keep orchestrate and backlog-run

Both stay user-level playbooks with their own state.

- **Pros:** nothing to rebuild.
- **Cons:** the failures above stay; every project copies the manager.
- **Complexity:** low.
- **Reversibility:** high.

## Consequences

- A project's specs are its vault ([adr/0001](0001-specs-tiers.md)): type directories
  at the vault root beside plans and items; a project that keeps specs in its repo has
  `setup` link them into the vault. booping's shipped core records stay in `specs/`
  beside `playbooks/`.
- `orchestrate` and `backlog-run` (with `backlog-manage`) are retired once
  project-manager covers them; hermes-pet's orchestrate specifics move into its specs.
- Confirmation: in a project with items, `/playbook project-manager` opens with the
  computed status; a user message with two requests files two items; an autonomous
  run takes ready items through groom and develop.
- 2026-10-17 (owner): the budget gate, time window and paused runs that plan 202610152053_project-manager-autonomous-extras carried over from backlog-run are out of booping's scope and leave the core; the size batching stays.
