## The task

Every model runs the same groomed plan from the same commit: port the `frontmatter-update` CLI's unit suite to the repository's txtar end-to-end corpus, then delete the superseded unit file. Three milestones — core CLI cases, list-operation and macro cases, then a coverage cross-check followed by the deletion. The model gets a green workspace and no human to ask.

## Sprint narrative

One session, 32m01s, 102 tool calls — half again the wall clock and roughly double the tool calls of either sibling at this tier. The extra work was not thrash: it was a third milestone that did its job properly.

**M01 — core CLI cases.** Nineteen cases: scalar sets, one case per coercion family, the YAML-1.1 `yes` quirk, an ambiguous `12:30` string, the eight syntax-sensitive values in one call, the newline/tab gap case via a stubbed macro, and the error and output-contract cases including the `[..]`-wildcarded log line.

**M02 — list ops and macro cases.** Twelve cases: the append family including idempotency across two sequential `cmd` lines, removal, the combined multi-operation call, stubbed macros with their error paths, and a real `["echo","1"]` argv macro whose asserted value can only come from execution.

**M03 — cross-check and deletion, and this is the run's distinguishing moment.** While building the coverage cross-check the model found three CLI-observable behaviours the M01 and M02 sets had never asserted — `value-with-an-equals-sign-is-preserved`, `empty-key-exits-1`, `set-a-key-to-an-empty-value` — and wrote them before deleting anything. Both sibling runs left `empty-value-lands-as-an-empty-string` unported; this one caught its own gap and closed it. That is precisely the failure mode the cross-check milestone exists to prevent, working as designed.

Then all 58 unit tests and parametrizations mapped to a case or a recorded drop rationale, the unit file deleted, stale-reference grep clean.

Work came back uncommitted; the runner made the commits (`8c77197`).
