## The task

Every model runs the same groomed plan from the same repo state, in its own throwaway clone, on its own branch, without asking anything of a human. The plan migrates `booping frontmatter-update`'s 571-line unit suite into txtar contract cases under `booping-python/e2e/cases/frontmatter-update/`, then deletes the unit file once a written cross-check justifies every deletion. Three milestones: core CLI cases, list-op and macro cases, and the deletion with its coverage cross-check. Nothing about the CLI's behaviour changes — the whole exercise is whether the model can move a contract from one test shape to another without losing any of it.

## Sprint narrative

**M01 — core CLI corpus cases.** One attempt, 8m57s, 56 tool calls, commit `faf9a5a`. The worker wrote 17 cases covering scalar set, the coercion families, and the error and output contract, then filled every assertion by rebaselining with `--txtar-update` rather than hand-writing expected bytes. Two of its own drafts were wrong and the rebaseline corrected them: `macro_stubs` sits at the top level of the merged config, not under `core:`, and the newline/tab value lands as a double-quoted escaped scalar. It caught both by reading the recorded contract back. The blemish is the method itself — six of its edits went into a blind rebaseline, writing assertions the model had not predicted, and that alone cost the entire 20-point rebaseline component of the agentic score.

**M02 — list-op and macro corpus cases.** One attempt, 7m55s, 53 tool calls, commit `c1636ce`. Twelve cases: the append family, `--remove`, the combined call, stubbed-macro interpolation with its two exit-2 failure paths, and a real macro declared as `echo 1` in fixture config so the asserted value can only come from executing it. This milestone rebaselined nothing blindly — the worker seeded each case with a deliberately wrong tail, forced a rewrite, then reviewed each generated diff by hand before the clean run. It also flipped its own milestone DoD checkboxes and task rows, which is vault bookkeeping the runner owns; the content was validated against the diff independently, so it changed no score, but it is a boundary the harness expects the worker to respect.

**M03 — delete the superseded units.** One attempt, 8m11s, 17 tool calls, commit `53348c3`, with one 49-second generation freeze. The worker wrote `coverage-cross-check.md` — 58 rows, one per test function and parametrization in the deleted file, each carrying either a case filename or a drop rationale — deleted `frontmatter_update_test.py`, and swept for stale references. The mechanical part is clean: 144 unit tests still pass, 29 corpus cases pass, the grep returns nothing outside historical vault records. The judgement part is where this run loses its points: five of those rows claim coverage that the named case does not provide, and M03 closed on them.

## Corpus quality

29 cases, all four-channel — every one asserts exit code, stdout, stderr and resulting file bytes together. One wildcarded line in 478 asserted (ratio 0.0021): the log-line timestamp, and nothing else. That is unusually tight; a corpus that wildcards more is a corpus that has stopped pinning things.

Exact-name recall against the frozen etalon list was 5/34. Mapped by behaviour it is 29/34 (85.29%). The gap is entirely naming: this model renamed almost every case, mostly toward its own convention of naming the assertion rather than the behaviour (`missing-plan-exits-1` for `missing-plan-file-is-rejected`, `bool-lands-unquoted` for `boolean-value-lands-unquoted`). A case-mapping judge recovered 24 of the 29 by reading the bodies. Gap coverage is 2/3 mapped, up from 0/3 exact.

Five etalon behaviours have no branch case at all, under any name:

- `empty-key-in-a-pair-is-rejected` — nothing runs `=value`; only the no-`=` variant is pinned
- `empty-value-lands-as-an-empty-string` — nothing sets `key=` to an explicit empty string
- `malformed-append-pair-is-rejected` — nothing feeds `--append` an argument without `=`; this is also one of the three designated gap cases the plan asked for by name
- `partly-numeric-value-stays-a-plain-string` — nothing writes a digit-leading string like `23 things`
- `value-may-contain-equals-signs` — nothing passes a value containing a further `=`

No orphan cases: every branch case maps to an etalon behaviour or was an exact-name match.

## Review

Two reviewers on the same rubric, both handed the case-mapping table so an unported behaviour reads as a finding rather than an absence. Mean 3.63/5.

| reviewer | grade | sub-grades |
| --- | --- | --- |
| `fable:medium` | 4.0 | correctness 3, tests 4, code 5, scope 4 |
| `codex` | 3.25 | correctness 3, tests 3, code 4, scope 3 |

Convergent findings, worst first:

1. `coverage-cross-check.md` maps `23 things` (partly-numeric string) onto `sets-a-key-with-a-literal-value.txtar`, whose value contains no digits — and M01's DoD line asserting a case per coercion family is ticked anyway.
2. The empty-value half of `test_remove_key_and_add_empty` maps to `remove-drops-a-key.txtar` and the combined case, neither of which sets an empty value.
3. `test_empty_key_exits_1` maps to `malformed-pair-exits-1.txtar`, which only runs `noequals`; `=value` is a distinct input the row itself half-admits is unpinned.
4. No case feeds `--append` a pair without `=` — a designated gap case, with M02's DoD line asserting full append coverage ticked.
5. `test_value_with_equals_sign` is dropped as internal, though split-on-first-`=` is CLI-observable and the cited replacements never pass such a value.
6. `remove-drops-a-key.txtar`'s fixture carries no YAML comment, so the inline-comment survival its cross-check row claims is asserted nowhere.

The pattern in one sentence: the defect is not in the corpus that was written — which is accurate, four-channel and mutation-hardened — but in the artifact whose entire job was to justify deleting the units, and M03 was closed on rows that overstate what the corpus proves.
