# Refactor /chat skill to groom pattern

## Context

`/chat` is flagged stale in the repo's `CLAUDE.md` alongside `develop`, `retro`, `learn`, `install`, `help`. `skills/groom/SKILL.md` was refactored first and is the canonical shape: Preflight loads reusable partials from `docs/partial_*.md`, the workflow is broken into explicit phases, and the skill body stays stack-agnostic. `/chat`'s current body still references `docs/project-scoping.md` (does not exist — replaced by `partial_project_resolution.md`), `projects.json` (replaced by `.booping` marker), `backlog/` paths (renamed to `plans/` per the plans-as-data refactor), a "never update `sprints.md`" rule (obsolete — `sprints.md` has no owner today and is drifting), and hand-offs that take `<backlog-path>` arguments. The user-facing effect is that a fresh agent reading `skills/chat/SKILL.md` gets a mix of live and dead instructions.

During grooming, scope expanded once: `/chat` is not a read-only discussion mode — it's the general working mode for small maintenance and ad-hoc coding tasks. The refactor needs to make that explicit (allowed writes, escalation rule to `/groom` when scope grows) rather than pretending chat is read-only while the user actually edits via it. An orient-phase command also revives `sprints.md` as a live rollup: `/chat` runs `booping-plans --format=md > sprints.md` on each session. `booping-plans` gains a `--format` flag for this; the `tsv` format stays the default to preserve current script-friendly piping.

## Business goal

After this sprint: a fresh agent reading `skills/chat/SKILL.md` sees a Preflight that points at live partials, a phased workflow that matches the `/groom` shape, hard rules that name what chat may and may not touch, and no broken references. The user running `/chat` on any project gets an opening message that includes a status summary of the vault (via the refreshed `sprints.md`) without any manual regeneration step. Stale files and comments that contradict the new contract are gone.

## Design

### Architecture

Two files change and one gets added to:

- **`bin/booping-plans`** — add a `--format {tsv,md}` arg to `argparse`. When `md`, replace the tab-join output with markdown-table emission: a `|`-separated header row, a `|---|---|...` separator row, then `|`-separated data rows. Prepend the documented header comment. Column resolution logic, status filter, sort logic, and exit codes are untouched.
- **`skills/chat/SKILL.md`** — full rewrite against the groom-shape template. New `## Preflight` loads partials. A `## High-level workflow` enumerates phases. `## Phase 0 Orient` runs the refresh + summary. `## Phase 1 Ingest` reads artifacts referenced in `$ARGUMENTS`. `## Phase 2 Discuss / act` permits small edits. `## Phase 3 Hand-offs` lists escalation targets. `## What chat does NOT do` and `## Hard rules` close the file. Tool allow-list trimmed: `Read, Write, Edit, Glob, Grep, Bash(booping-plans:*), Bash(ls *), Bash(git status *), Bash(git log *), Bash(git diff *), Bash(cat ~/Claude/*), AskUserQuestion, Agent`.
- **`CLAUDE.md`** — one-line update to the "Plan lifecycle" bullet that currently says "There is no `sprints.md` rollup."

No new partial is created. The `sprints.md` regeneration rules live inline in chat's Phase 0 — the only consumer of those rules is chat itself. Other skills inherit the "never hand-edit sprints.md" rule via the repo `CLAUDE.md` update.

### Decisions

| # | Decision | Alternative considered | Why this one |
|---|----------|------------------------|--------------|
| D1 | Add `--format` to `booping-plans`; default stays `tsv` | Emit `md` unconditionally / switch the default to `md` | Script-friendly TSV piping is still a real use case; the flag preserves both. Default-`tsv` keeps current callers byte-identical. |
| D2 | Regenerate `sprints.md` from inside `/chat` Phase 0 (not a dedicated CLI subcommand) | Revive `booping-plans sync-sprints` as a first-class subcommand | Cache invalidation is simple: `/chat`'s orient is the canonical refresh point and the user opens `/chat` to survey state anyway. A subcommand adds surface area that no other skill needs. |
| D3 | Inline `sprints.md` rules in chat `SKILL.md`; **do not** create a `partial_sprints_snapshot.md` | Extract to a new partial for "reuse" | There is exactly one consumer (chat). A partial with one consumer is a premature abstraction. The cross-skill rule ("never hand-edit") lives in repo `CLAUDE.md` instead. |
| D4 | Relax chat from "read-only" to "small writes allowed, escalate to `/groom` when scope grows" | Keep chat strictly read-only | User confirmed chat is already used for ad-hoc coding / vault maintenance. Pretending it's read-only left rules that contradicted real usage. |
| D5 | No `partial_plan_transitions_chat.md` | Write one anyway for symmetry with `/groom` | Chat owns zero plan-status transitions. Writing an empty transitions partial would be performative. The `/groom` skill's transitions partial stays the only one until another skill owns transitions. |
| D6 | Legacy-content audit runs across `agents/*.md` + `skills/*/SKILL.md` | Audit only chat's own file | Lesson 0006 requires enumeration when a flow changes; swapping `sprints.md` ownership is a flow change even if chat is the sole new writer. |
