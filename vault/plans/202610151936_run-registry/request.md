**Task type** — `feature`: a new user-facing capability — `booping run groom|develop` launches a recorded headless run, and `booping status` gains a runs section. Not `bug`: nothing observed diverges from documented behaviour — no launcher or registry exists to be wrong. Not `refactoring`: new command surface and a new vault artefact appear; the no-behaviour-change test fails.

**Problem** — Today a headless groom or develop run is launched by hand-typing `claude -p` with the right env (`CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0`), `< /dev/null`, a pasted autonomy preamble and a hand-picked log path; nothing records that the run exists, which item it serves, or how it ended, so a finished run goes unnoticed until someone asks (adr/0028: finished runs sat unnoticed for 15 hours). adr/0028 decides every launched run is registered with its item and a fallback check, and a finished run surfaces on the next turn. After this plan one command launches and records a run, and `booping status` shows running, finished-not-yet-seen and lost runs.

**Clarifications and Decisions** (autonomous run — every one is a default, logged in `clarifications.md`)

- C1 — command: `booping run groom TARGET...` (open item ids, or one plan path to resume a parked groom) and `booping run develop PLAN`, both with `--autonomous`; `booping run ack ID...` marks a finished run seen.
- C2 — the launch is foreground: `booping run` waits for `claude -p` and exits with its code; the caller backgrounds it (the Bash tool's background mode, a timer). No daemon, no detached process.
- C3 — registry: one plain-markdown record per run at `{vault}/runs/{id}.md` (rule/0028), its log beside it as `{id}.log`; `runs/.gitignore` keeps logs out of git.
- C4 — record fields and their only writer: `booping run` writes `running` at launch and `finished`/`failed` with the exit code at the end; `lost` (record says running, process gone) is computed at read time — the fallback check.
- C5 — launch shape in config `core.run` (shared key): `command` argv, `env`, `prompt`, `preamble`, `dir` — overridable per tier; no value env-interpolated.
- C6 — session id and run id are deterministic: run id from the date macro, session id a uuid5 of the run id passed as `--session-id`.
- C7 — the items: develop records the items planned for the plan; groom records the item ids it was given, or the items planned for the given plan.
- C8 — status: a `runs` section after `plans` — running, unacked finished/failed, lost.
- C9 — exact output content locked in the plan's I/O contract (rule/0010).
- C10 — out: budget/window gates, batching, a timer, the project-manager playbook (part 4), project-manager docs and setup linking (part 5), resuming a session.
