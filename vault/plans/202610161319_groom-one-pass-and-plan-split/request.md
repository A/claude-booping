## Task type

`feature` — groom gains a new shape (one drafting pass, a script-made milestone layout, a post-split contract check) and the CLI gains `booping plan split`, both user-facing. Not `bug`: nothing observed diverges from expected; the current groom works, it is slow and costly (adr/0030 Context). Not `refactoring`: the change is visible to the user — groom's steps, cost and the new command change, and only the output contract (`index.md` + milestone files) stays fixed.

## Problem

Today groom drafts a plan over several detached steps (research-codebase, research-web, draft-plan writing `index.md` plus one scaffolded milestone file at a time, cross-review), costing 13–23 min and $4.25–5.62 per plan and carrying ~45 prompt rules, 16 of which the model follows unprompted. After the change groom drafts the whole plan as one file in a research-then-draft pass (V3a), a deterministic `booping plan split` cuts it byte for byte into `index.md` and the milestone files develop already reads, and a code-run milestone contract check sends a failing milestone back to the draft; only a plan the script flags goes to a Sonnet split.

## Clarifications and Decisions

- Autonomous run: every default is recorded as an answered question in `clarifications.md`.
- Outcome after shipping: a groom run is faster and cheaper at V3a quality, and the plan's text reaches the milestone files unchanged (adr/0030, adr/0031 Criteria).
- Out of scope: renaming the milestone file to `milestones/M{nn}-*/index.md`; the light path for small requests.
