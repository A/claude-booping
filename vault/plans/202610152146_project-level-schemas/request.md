# Request

**Request**

> Request — project-level schemas (adr/0001: a tier adds and overrides). A project writes its records in its own language and may need its own record types: the new repo swarmlight writes specs in Russian (headings like `## Правило`, `## Следует из ценностей`, `**На практике:**`) and the shatterlings PoC had an extra `mechanic` type. Build: a project (and the global tier) can carry its own mdcheck schemas — e.g. `<tier root>/_schemas/<type>.yaml` (pick the location so it never collides with record type directories at the vault root, and record the choice) — which override the shipped schema of the same type for that tier and add new types; `booping specs check|ls|next|site`, rule injection and open-items scan use the effective type set per tier; frontmatter fields the code reads (type, status, targets, brief, values, rules, supersedes, sources, kind, reviewed) stay language-neutral. Ship a Russian schema set as a ready example under src/specs/ (e.g. src/specs/schemas-ru/) that `booping specs init` can copy into a tier on request (`--schemas ru`), with the hermes-pet headings as the reference (/home/anton/Dev/@A/hermes-pet/specs/schemas/*.yaml, read-only). Tests: txtar cases for an overriding schema, an extra type, and init --schemas ru. Docs.
> Target repo facts (swarmlight, reported from the other machine; its specs live in repo `specs/`, schemas in `specs/schemas/*.yaml`, checker was the shatterlings Rust `crates/specs`): types values (3 area files, `## Ценности` with an H3 per value, `**На практике:**`/`**Чем жертвуем:**`), rule 22, story 30, conflict 7, adr 9, mechanic (schema only: status {live,planned}, tags ≥1, H2 `Как устроено`, `Где живёт`, `Открыто?`); summary ≤160; a `tags` field on most types checked against `tags.yaml` (`area[:sub]` kebab-case dictionary); adr Альтернативы table `Вариант|Статус|Сложность|Обратимость|Вердикт` with H3 per row. Its old checker also did cross-file checks we lack: table rows ↔ H3 blocks, exactly one accepted variant, anchors resolve. In this plan also: (a) a `tags` field checked against a per-tier `tags.yaml` dictionary when the tier has one; (b) the ADR alternatives checks (rows ↔ H3, exactly one accepted) driven by schema-level names so they work for the Russian set too; (c) the Russian set covers the area-file `values` form only as an import path: `booping specs` scenario guidance on splitting an area file into one record per value (judgement stays with the model), not a schema for it.

**Task type** — `feature`: a tier gains a new capability — its own schemas overriding and extending the shipped format, a tags dictionary, ADR alternatives checks, and a shipped Russian schema set `booping specs init --schemas ru` installs. Not `bug`: the shipped format behaves as documented; adr/0001 and value/0005 promise tiers that add and override, but nothing documented diverges in what ships. Not `refactoring`: new files a tier may carry, new check errors and a new init flag appear; the no-behaviour-change test fails.

**Problem** — Today every tier is checked against the one shipped schema set (`core.specs.format` → `src/specs/schemas/{type}.yaml`); the record types are its schema stems, the same for core, global and project. A project writing its records in Russian, or carrying a type booping does not ship (`mechanic`), fails `booping specs check` and cannot be listed, numbered, sited or scanned. adr/0001 and value/0005 say a tier adds and overrides; for schemas it cannot. After this plan a tier may carry its own schemas that override a shipped type's shape for that tier and add types; every `booping specs` surface, rule injection and the open-items scan read the effective type set per tier; a tier with a `tags.yaml` has every record's `tags` checked against it; ADR alternatives are checked across the file (table rows ↔ H3 blocks, exactly one accepted option) under names the schema sets, so a Russian set works too; booping ships a Russian schema set `booping specs init --schemas ru` copies into a tier, and the specs playbook guides splitting an area-file `values` record into one record per value. Frontmatter keys and the status/kind values code reads stay language-neutral.
