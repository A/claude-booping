# Plans-as-data refactor

## Context

Today the plan lifecycle is split across hand-edited markdown in `backlog/`, a hand-edited `sprints.md` table, and retrospective frontmatter that references `backlog:` paths. Every skill has a "now update sprints.md" block that drifts in practice: rows get out of date, `Goal Status` lives only in the sprint row (not the plan), and there is no single source of truth for "what is pending?". This sprint turns each plan file into the canonical record (frontmatter = state), adds a `booping-plans` CLI that skills call for state transitions, makes `sprints.md` a wholesale-regenerated rollup, and introduces a 9-state lifecycle (`backlog → in-spec → ready-for-dev → in-progress → awaiting-retro → awaiting-learning → done`, plus terminal `fail` and `cancelled`). Renaming `backlog/` → `plans/` is bundled in because "backlog" is now a *status*, not a directory. There is no migration script — existing vaults are upgraded by the agent on demand using the same `booping-plans set` CLI this sprint ships.

This plan itself bootstraps before the CLI exists: its `status: in-spec` is hand-written. Once M1 lands, every future plan gets created in `status: backlog` and moved via CLI.

## Business goal

Anton runs `/groom`, `/develop`, `/retro`, `/learn` and never touches plan frontmatter or `sprints.md` by hand. When he runs `/chat` he sees accurate counts of what is planned, in-progress, awaiting-retro, and awaiting-learning — without reading any file himself — and the rollup matches the plan files because it is regenerated on every transition.

## Design

### Architecture

The plan file frontmatter is the canonical state record. One plan = one markdown file in `~/Claude/{project}/plans/`. State transitions flow through a single CLI entry point, `bin/booping-plans`, which skills invoke instead of hand-editing frontmatter or `sprints.md`.

Integration points:

- **`bin/booping-plans`** (new) — Python uv-shebang wrapper that delegates to `bin/booping_plans.py` (importable module). Subcommands: `list`, `set`, `sync-sprints`. Writes are direct (no tempfile+`os.replace` — see D4).
- **`~/Claude/{project}/plans/*.md`** — canonical plan files. Frontmatter schema below. Body is free-form markdown per `skills/groom/template.md`.
- **`~/Claude/{project}/sprints.md`** — wholesale-regenerated rollup. First line is a plain-text regeneration notice (e.g. `Generated by booping-plans sync-sprints — do not hand-edit; run the CLI to update.`). Active section on top, History below.
- **`bin/booping-init`** — creates `plans/` (not `backlog/`) and writes an initial `sprints.md` with the notice header and empty Active/History skeletons.
- **`docs/plan-schema.md`** (new) — canonical reference for the 9-state lifecycle, transition rules, and frontmatter schema. Skills link to this doc instead of duplicating the rules.
- **Skills (`skills/{groom,develop,retro,learn}/SKILL.md`)** — each replaces its manual frontmatter/sprints edit with a `booping-plans set …` call followed by `booping-plans sync-sprints`. Documented per-command fallback that hand-edits and prints stderr verbatim when the CLI exits non-zero.
- **Retro frontmatter** — key `backlog:` renamed `plan:`. `/learn` reads this field to locate the plan when flipping `awaiting-learning → done`.

Frontmatter schema:

| Field | Required | Default | Writer | Purpose |
|---|---|---|---|---|
| `title` | yes | — | /groom | Display name |
| `type` | yes | — | /groom | `feature` \| `bug` \| `refactoring` |
| `status` | yes | `backlog` (initial) | /groom,/develop,/retro,/learn | Lifecycle state (9 values, see below) |
| `sp` | yes once `ready-for-dev` | — | /groom | Total SP |
| `source` | yes | `ad-hoc` | /groom | Origin |
| `created` | yes | today | /groom | Immutable creation stamp |
| `planned` | yes once `ready-for-dev` | today-of-transition | CLI auto-fill | Date the plan was committed to a sprint |
| `started` | optional | today-of-transition | CLI auto-fill | Set on `→ in-progress` |
| `completed` | optional | today-of-transition | CLI auto-fill | Set on `→ awaiting-retro`, `→ fail`, `→ cancelled` |
| `retro` | optional | — | /retro | Path to retro file |
| `goal` | yes once `awaiting-learning` | — | /retro | Enum: `success` \| `partial` \| `fail` |
| `business_goal` | features only | — | /groom | User-visible outcome |

Lifecycle states (9): `backlog → in-spec → ready-for-dev → in-progress → awaiting-retro → awaiting-learning → done`, plus terminal `fail` and `cancelled`. Defined in full in `docs/plan-schema.md`.

- `backlog`: plan file exists; raw draft, research stub, or parked idea. `/groom` writes plans here initially; the user can also manually move finished work back to `backlog` (e.g. a cancelled idea reconsidered later by moving from `cancelled`).
- `in-spec`: `/groom` is actively spec'ing this plan (agents rewriting, validator running).
- `ready-for-dev`: `/groom` accepted by user, validator clean; `/develop` can claim it.
- `in-progress`: `/develop` picked it up.
- `awaiting-retro`: `/develop` marked done; waiting for `/retro`.
- `awaiting-learning`: `/retro` written; waiting for `/learn`.
- `done`: `/learn` has absorbed lessons. Terminal success state.
- `fail`: technical execution failure. Terminal.
- `cancelled`: explicitly shelved by the user before completion. Terminal.

CLI contract (intentionally small — limited to what the skill set needs):

- `list --project=<name> [--status=<value>]` — enumerate plans. Human-readable table on stdout (columns: `status`, `sp`, `type`, `title`, `path`). Malformed YAML in one file: warn + skip, overall exit 3.
- `set --project=<name> <plan-path> <key>=<value> [<key>=<value> …]` — validate and write one or more frontmatter keys. Parses each argument with `arg.split('=', 1)` so values may contain `=`. Validates enum keys (`status`, `goal`, `type`) and date keys (`YYYY-MM-DD`). Auto-fills `planned`/`started`/`completed` on the matching status transitions only when the key is not currently set and not passed explicitly.
- `sync-sprints --project=<name>` — regenerate `~/Claude/{project}/sprints.md` wholesale: compute active + history tables from plan frontmatter, emit file. Deterministic ordering (sort by `planned`/`completed`, tie-break by filename). Run-twice byte-identical.

`--project` is always required. When omitted, the CLI exits 4 with stderr: `error: --project is required. Usage: booping-plans <subcommand> --project=<name> [...]. Example: booping-plans list --project=claude-booping`.

Exit codes: 0 ok, 1 generic, 2 file-not-found (never creates), 3 malformed-frontmatter (non-fatal: list/sync-sprints), 4 missing-project-arg, 5 invalid-enum-value, 6 malformed-frontmatter (fatal: set).

Writes only: `~/Claude/{project}/plans/*.md` frontmatter and `~/Claude/{project}/sprints.md`. Never touches `lessons/`, `retrospectives/`, `metrics/`, or any other directory.

### Decisions

| # | Decision | Alternative considered | Why this one |
|---|----------|------------------------|--------------|
| D1 | Rename `backlog/` → `plans/` in this sprint | Ship CLI first, rename in a follow-up | Blast radius is the same ~20 files either way; doing it once avoids a second churn pass. "backlog" becomes a *status*, not a directory. |
| D2 | Single CLI (`booping-plans`) instead of per-skill inline Python | Each skill edits frontmatter itself | Centralises validation, enum rules, and ordering logic; enables tests. Skills gain a subprocess hop, which is cheap. |
| D3 | `ruamel.yaml` over `pyyaml` | `pyyaml` (lighter dep, no round-trip) | Plan frontmatter has inline `#` comments in the template; we want `set` to preserve them. `pyyaml` would flatten. |
| D4 | Direct write (no tempfile + `os.replace`) | Atomic write via tempfile + rename | Skills run serially inside a single Claude Code session; concurrent writers don't exist. Crash-during-write is vanishingly rare and git/diff recovers. Atomic-write machinery is overkill for a single-user CLI. |
| D5 | Keep both `awaiting-retro` and `awaiting-learning` | Collapse into one | Retro doc and lesson extraction happen at different times; two states make "what is pending?" queries accurate. |
| D6 | No migration script. Upgrades are manual via the same CLI this sprint ships | Ship a one-off `booping-migrate-plans` | Migration is rare (per-vault, one-time), touches files across directories, and would duplicate logic. An agent can `git mv backlog/* plans/` and run `booping-plans set ...` on each file; that's simpler and inspectable. |
| D7 | `sprints.md` wholesale regen with a plain-text notice header | HTML-comment managed-by markers with refuse-to-clobber | The managed-block pattern adds complexity without enough value — `sync-sprints` runs often and the notice header is a clear enough signal. Users who want custom notes put them in a separate file. |
| D8 | `planned` date separate from `created` | Reuse `created` everywhere | A stub created at split time can sit in `backlog` for weeks before being committed to a sprint; "when was this committed?" is the useful sort key for Active. |
| D9 | Skill-level fallback: hand-edit frontmatter + print stderr verbatim on CLI non-zero exit | Hard-fail the skill on CLI error | The CLI is new and in the critical path; a fallback keeps the user unblocked while making CLI bugs loud. Per-command fallback (distinct handling for `set` vs `sync-sprints` failures). |
| D10 | Add `cancelled` as a terminal state distinct from `fail` | Collapse into `fail` | `fail` is a technical-execution outcome; `cancelled` is a product/priority decision. Retro/learning wants to treat them differently (cancellation is not a lesson source). |
| D11 | `booping-plans` validation is value-level only (enum values, date formats, parse-time schema) | Also validate cross-field invariants | Keeps the CLI a thin, deterministic transform. Cross-field invariants (e.g. `sp` required once `ready-for-dev`) are enforced by `/groom`'s quality checklist and the future `/booping:lint`. |
| D12 | `booping-plans set` mutates existing files only; never creates | `set` implicitly creates when path is missing | Creation is owned by `/groom` (primary plan + sibling stubs) where filename derivation and body template live. A `set`-that-creates would let typo'd paths silently spawn empty plans. |
| D13 | `--project` is required; no resolution chain | `.booping-project` marker + `projects.json` longest-prefix match | Skills always know the project (they resolve it themselves via the project-scoping chain). The CLI being simple and explicit avoids duplicating that logic and makes error messages actionable. |
| D14 | `list` emits a single human-readable table format | Also support `--format=json` | YAGNI. Skills that need structured data can parse the table or read plan files directly. Dropping JSON removes `datetime.date` serialization complexity. |
