# Re-groom leaves the old plan ready-for-dev; groom cannot cancel a ready-for-dev plan

Source: [lightspace-android feedback](../researches/20261018-lightspace-android-feedback/index.md), point 9.

Re-grooming a plan created a new plan directory while the old one stayed `ready-for-dev`, and develop relaunched on the old path. The groom receipt should say "superseded X → Y" and mark X. A ready-for-dev plan can be cancelled only through develop's machine.

## Note (2026-10-18)

The cancel half needs no new edge: develop's machine already has `ready-for-dev → cancelled` (with the `open-items-follow-plan` hook), reached as `booping transition {plan}/index.md cancelled --playbook develop`. A second, groom-side edge would make every such call ambiguous between the two machines. Left open for the supersede half, which goes through groom.
