# Retrospective: Plans-as-data refactor

## What went well

- **Plan was dense enough to drive auto-mode without course correction.** The 14 SP / 6 milestone plan landed in a single session with no mid-sprint user intervention. Grooming-session pushback had already distilled the scope (D4 direct-write, D6 no migration script, D7 plain-text header, D13 `--project` required, D14 no JSON) so the implementation had no ambiguous decisions left to resolve.
- **M1 CLI hit its quality bar cleanly.** One cohesive ~500-line module, 33 unit + 3 integration tests green, line coverage 92% against the 85% DoD bar, ruamel round-trip proven (comments and block scalars preserved), None-safe sort with `datetime.date.min` sentinel. Exit codes and auto-fill rules match the plan's contract.
- **Dogfooded end-to-end.** This plan file lives at `plans/20260422-plans-as-data-refactor.md` with the full 12-field frontmatter, transitioned via `booping-plans set` through the lifecycle, and `sprints.md` was regenerated byte-identical across two consecutive runs. The sprint's artifacts validate its own CLI contract.
- **Terminology swap (M6.2) was thorough.** The grep-and-replace across agents, skills, docs, README, PRD, and the vault-local CLAUDE.md landed without personality edits creeping in; `just lint-backlog` now exits 0.
- **Fallback discipline was consistent.** Every rewired skill (`/develop`, `/retro`, `/learn`, `/groom`) has the per-command fallback block verbatim, so a CLI regression stays loud instead of silently stalling the workflow.

## What went wrong

### M6 verify block missed the `docs/plan-schema.md` links for legacy skills

**What happened**: The M6.1 DoD says *every* skill that references a status value must link to `docs/plan-schema.md`. M6 shipped with the links present only on skills the sprint actively rewired; `skills/groom/`, `skills/chat/`, `skills/learn/`, `skills/help/` were missed. Commit `c0c9c9b`, added after the sprint was otherwise done, patched them in.

**Why**: The M6 Verify block only grep'd the *new* skills. A DoD phrased as "every skill that references a status value" was never enumerated — the Verify block spot-checked instead of using `grep -L` against the full set.

**Impact**: A sprint-level DoD slipped past the M6 boundary and needed a cleanup commit, meaning the "done" line was crossed with known gaps. It also means we cannot trust "M6 passes Verify" to mean "DoD met" for that bullet.

### Orchestrator dogfood deviations

**What happened**: Two of the sprint's writes were performed by the orchestrator outside the skill's allow-list: (1) the sprints.md row for this plan was hand-added rather than produced via `booping-plans sync-sprints`, (2) a 1-line edit to `docs/plan-schema.md` was applied directly instead of re-delegated to a worker.

**Why**: The orchestrator's edit allow-list in `/develop` is narrow (plan file progress marks, `sprints.md`, `metrics/lesson-hits.md`). For a sprint whose business goal was *centralizing state transitions through the CLI*, the orchestrator should have been *more* strict, not less. The deviations were convenient; nothing flagged them as a boundary crossing.

**Impact**: The CLI-only invariant got a hairline crack in its own founding sprint. A contributor reading the git history sees the orchestrator bypassing the very contract the sprint established. The sprints.md row question is not harmful because the CLI would have produced the same content, but the `docs/plan-schema.md` edit was a precedent nobody wants to cite later.

### Reviewer follow-ups accumulated in Risk register instead of being re-delegated

**What happened**: M1 reviewer surfaced ≥7 follow-ups (exit-code naming drift, `argparse.error()` collision with `EXIT_NOT_FOUND`, body-only .md regression gap, scattered user-facing error strings, hardcoded project-root helper missing, `pyproject.toml` for `uv run` re-resolution, `set sp=` empty-value polish). All were appended to the Risk register row "M1 reviewer follow-ups deferred to S2 polish" and none were fixed in-sprint.

**Why**: No rubric on when a reviewer follow-up becomes a worker re-delegation vs a deferred note. Default behavior collapsed to "document, don't fix", which is the path of least resistance when scope is tight.

**Impact**: S2 starts with a noticeable polish debt that is specifically in the dependency path of skill reliability (error-string contract, argparse collision). One item (the argparse exit-code collision) is a latent bug: `booping-plans` with bad argv will exit 2, which the skill fallback will interpret as EXIT_NOT_FOUND.

### Skill-body and init-smoke regression coverage is manual or grep-only

**What happened**: QA found no automated harness that executes the CLI commands documented inside `skills/*/SKILL.md` bodies. `just lint-backlog` greps forbidden tokens but no test exercises the documented invocations. `bin/booping-init smoketest` is run manually; it is not wired into `just check`.

**Why**: The sprint scoped testing around `bin/booping_plans.py` (M1.5) but treated skill bodies as prose. The dogfood check in the DoD ("this sprint's own files live under `plans/`") is a one-off assertion, not a harness.

**Impact**: A copy-paste typo in a skill body — e.g. `booping-plans set status=in_progress` (underscore) — would ship green through `just check`. The fallback block would catch it at runtime, but the intent was to keep the CLI path hot; a regression that silently relies on fallback is invisible.

### Agent files carried stale content that M4/M6 didn't audit

**What happened**: Found during post-retro review of the shipped files: (1) `agents/booping-be-dev.md` and `agents/booping-fe-dev.md` descriptions carried project-specific stack names — Python/Django/DRF/Rust/Axum/migrations/Celery/Temporal on the backend, React/TypeScript/components/state/styling/Leptos on the frontend — even though booping is meant to be project-agnostic and stack specifics belong in per-project `~/Claude/{project}/_booping/agent_<name>.md` extensions. (2) `agents/booping-teamlead.md` still claimed ownership of `sprints.md`: description tail read "…drafts retrospective documents, and maintains sprints.md", a responsibility bullet said "Own `sprints.md` — when instructed by the `/develop` skill, update the sprint table", and the hard-rule edit allow-list listed `sprints.md` first. After M4, none of that is true — `booping-plans sync-sprints` owns the file and teamlead writes retro prose only.

**Why**: M6.2 was briefed as a terminology-and-path swap (backlog→plans) and was explicitly told NOT to touch agent personalities or descriptions beyond that phrasing. The description-line stack leakage predates this sprint, and the teamlead ownership claims predate M4's data-flow change — neither was in M6.2's touched-file list. No milestone had "audit plugin-shipped agents against the new data-flow" as a DoD bullet, so the files were never re-read against current reality.

**Impact**: A user installing the plugin into a non-Python/non-React project would see a backend agent advertising Django/Celery and a frontend agent advertising Leptos, which pulls the agent selector toward the wrong tool. The teamlead ownership claims would have actively caused harm — any teamlead instance reading its own hard-rules would believe hand-editing `sprints.md` is allowed, directly contradicting the sprint's central invariant.

### docs/plan-schema.md over-verbose on first write

**What happened**: Found during post-retro review: M6.1 delivered `docs/plan-schema.md` at 109 lines with a full from→to transitions table, per-field prose expansions below the frontmatter table, and three lifecycle-exception bullets. The transitions table duplicated rules already documented inside the skill bodies, and the per-field prose re-said things the 12-field frontmatter table's Purpose column already captured.

**Why**: The M6.1 brief set a target of "≤250 lines" (generous) and enumerated every section to include — but gave no guidance on "what to cut if sections overlap with existing skill docs". The worker optimized for completeness against the enumeration, not for minimality against the doc set as a whole.

**Impact**: Moderate — the schema doc is the canonical reference for the 12-field contract, and duplicated content across it and the skills creates drift risk (next schema edit has to hunt down every copy). Compacting to 69 lines folded the per-field prose into the frontmatter table and replaced the transitions table with a 3-line happy-path arrow plus terminal-state note.

### Pre-sprint drift kept floating in the working tree

**What happened**: `skills/install/SKILL.md` has a modified-but-uncommitted chunk from before the sprint, and `.booping-project` is an untracked marker file. Both were deliberately kept out of sprint commits but never cleaned up or tracked.

**Why**: No decision point in the sprint asked "what about this drift?". The orchestrator focused on staying on-scope, which is correct for commit hygiene but leaves the worktree in a state that mildly corrupts `git status`.

**Impact**: Low direct impact, but it sets a pattern where drift accumulates. `.booping-project` specifically is a policy question (commit the marker or gitignore it) that will come up again.

## Root causes

- **Verify blocks are spot-checks, not universal quantifiers.** DoD items phrased "every X links to Y" or "every X satisfies Z" need enumeration commands (`grep -L`, find, test loop), not sample greps. M6 and the QA gaps share this pattern: a DoD says "every" but the Verify block says "some representative". The failure mode is silent — a green Verify means nothing if it never counted the universe.
- **Dogfood boundary on the orchestrator is ambiguous.** The `/develop` skill defines an edit allow-list, but when the sprint's subject is "centralize state via a CLI", the orchestrator's allow-list and the sprint's invariant overlap. There is no written rule that says "if the sprint's own business goal restricts who writes to file F, the orchestrator is also bound by that restriction, even if F is on its allow-list for other sprints". The sprints.md hand-edit and the docs/plan-schema.md 1-line edit both sit in this gap.
- **Reviewer→worker re-delegation has no cost/benefit rubric.** The default is "log it in the Risk register and move on", which optimizes for sprint throughput and against sprint quality. Without a severity threshold ("S0-S1 fix now, S2 defer") or a numeric budget ("no more than N follow-ups deferred per milestone"), every follow-up defaults to deferred.
- **Milestone briefings as boundary-setters, not scope-limiters.** M6.2's briefing forbade personality and description edits to keep the terminology-swap milestone tightly scoped — a sensible boundary for a mechanical pass. But a narrow boundary on a cross-cutting milestone (touching every agent + skill + doc) also forbids auditing latent stale content, so drift accumulated before the sprint gets locked in under a green Verify. When a refactor crosses a data-flow boundary — who writes file F, who reads it, when it's generated — the mechanical-swap pass and the legacy-audit pass should be separated, or the swap agent should at least be asked "does anything here contradict the new flow?". This is a grooming-level pattern: for cross-cutting sprints, add an explicit "legacy-content audit" DoD bullet rather than relying on the swap pass to catch it incidentally.

## Takeaways

- **"Every X" DoD items need enumeration, not sampling.** If the DoD uses a universal quantifier, the Verify block must enumerate the universe (`grep -L`, find loop, test over array). A spot check against 2–3 representatives will silently pass while leaving gaps.
- **When the sprint's invariant is "only the CLI writes file F", the orchestrator is bound by the invariant even if F is on its usual allow-list.** Delegate even 1-line edits for the duration of a lifecycle-data sprint; the allow-list is a ceiling, not a floor.
- **Reviewer follow-ups need triage at creation, not at retro.** If more than 3 items accumulate in a Risk register row during a single milestone, route them to an explicit S2 plan instead of leaving them as a flat list — or decide per-item fix-now vs defer-now. The default should not be "append and forget".
- **Lint recipes are load-bearing for contract stability.** When skills grep verbatim CLI stderr strings, pin them in a golden file immediately; the alternative is a silent drift where a rephrased error message breaks the fallback path without any test turning red.
- **Cross-cutting terminology/path-swap milestones need an explicit legacy-audit DoD bullet.** A "swap, don't audit" briefing is safer for the orchestrator to run autonomously — the worker has a crisp stop-rule and the blast radius is predictable — but it leaves landmines that only surface when a user reads the files later. For milestones that touch every agent + skill + doc, the grooming DoD must include an "audit stale ownership claims and stale stack names in agent files" bullet, scoped as a separate verification pass rather than folded into the mechanical swap.

### Candidate new lessons

- **Verify-block universal quantifiers** — Trigger: a DoD item uses "every", "all", or "each" against a file/symbol set. How-to-apply: the Verify block must enumerate the set and fail on any miss (`grep -L pattern files…` or a shell loop). Spot checks against 2–3 samples are not enough. Domain tag: `qa`.
- **Orchestrator delegation for sprint-scope files** — Trigger: the orchestrator is about to edit a file whose write-path is the *subject* of the active sprint's business goal (e.g. a sprint about "only the CLI writes `sprints.md`", and the orchestrator has hand-edited sprints.md on its allow-list). How-to-apply: stop and delegate even a 1-line change; log an exception with rationale if you proceed. Allow-list membership is not a license during invariant-establishing sprints. Domain tag: `all`.
- **Reviewer-follow-up triage rubric** — Trigger: a reviewer returns approve-with-followups. How-to-apply: decide per-item fix-now (blocking) vs defer-to-next-sprint (risk-register with explicit S2-plan pointer). Never accumulate more than 3 deferred items per milestone without promoting them to a named follow-up plan. Domain tag: `tech`.
- **Skill-body regression harness** — Trigger: a skill-body SKILL.md contains CLI invocations that users or agents depend on verbatim (command names, flag names, subcommand names). How-to-apply: add a pytest that execs each documented invocation against a `tmp_project`, asserts non-zero fails, and wire it into `just check`. Prose testing is grep, which misses everything but spelling. Domain tag: `qa`.
- **CLI error-string contract** — Trigger: skills (or their fallback blocks) grep verbatim strings out of a CLI's stderr. How-to-apply: pin those strings in `tests/golden/error_messages.txt`; the CLI test suite diffs against the golden on each run. Rephrasing an error message then becomes an intentional golden-file update, not a silent break. Domain tag: `code`.
- **Agent-body audit after data-flow changes** — Trigger: a sprint changes the canonical flow for a data artefact (who writes it, who reads it, when it's generated). How-to-apply: enumerate every agent and skill that previously touched that artefact; audit each one's description + hard-rules + responsibility bullets for stale ownership claims; fix in the same sprint rather than letting a terminology-swap milestone forbid touching them. Domain tag: `tech`.
