adr/0001  accepted  Specs are a core feature in three tiers: Booping ships the specs format and its own specs; a global tier in the home dir and a project tier in the repo add their records, cross-tier refs go by namespace.
adr/0002  accepted  Procedures are playbooks behind one skill: Every booping procedure ships as a playbook driven by the single /playbook skill; a new skill is written only for a surface /playbook cannot drive.
rule/0002  accepted  What is not in the source is marked, not invented: A record or artefact states only what its source says; an open point is marked [clarify] or "not named in the source", never filled in by the agent.
rule/0003  accepted  The compact artefact is reviewed before the detail: Where a human reviews, a run first produces a compact artefact the human can read and reorder, and builds the expensive detail only on the reviewed one.
rule/0005  accepted  Every step ends by naming the next one: A playbook step or a run that hands back to the user ends by naming the next step and how to call it; a premature call says what is missing.
rule/0012  retired  Every diff is reviewed in Plannotator, never in chat: In this project the code-review human step always runs through the plannotator-reviewer agent; a missing agent or a dead surface stops the run, never falls back to chat.
rule/0013  accepted  Snapshot baselines are accepted by the user, never by a run: A run never runs just snapshots-accept or writes the committed playbook reports; it leaves the drift uncommitted and names it in its final report for the user to accept.
rule/0015  accepted  Code review covers code files only: A code review surfaces findings on code files only; documentation, plans and other prose in the diff pass unreviewed.
rule/0017  accepted  Structured data is rendered from config, never restated in prose: Statuses, queues, agent ids, globs and other structured values live in config or query specs and are rendered into bodies; prose never copies a literal.
rule/0018  accepted  Project specifics stay out of the core: Core skills and playbooks stay stack-agnostic; whatever is specific to a project is written into that project's tier, never into the core or a user-level scope by a run.
rule/0019  accepted  The driver owns the vault and git; workers touch only repo code: The driver owns the vault, run state and commits; workers edit only repo code, never git history; a small fix goes to the session already holding its context.
rule/0020  accepted  Project shaping of an agent or skill is a targeted record: A project adjusts a core agent or skill through a targeted rule (agent:<id>, skill:<name>), never through a separate extension file.
rule/0022  accepted  Commits are conventional with a scope: Commit messages follow Conventional Commits with a scope, such as feat(booping) or fix(groom).
rule/0023  accepted  The README Statuses section follows the states blocks: The README's Statuses section is a hand-kept narrative over each playbook's states block; a change to a states block revisits it in the same change.
rule/0024  accepted  A new procedure is a playbook, not a skill: Anything procedural is added as a playbook driven by /playbook; a new skill is added only for a surface /playbook cannot drive.
rule/0025  accepted  Who reads the result decides prose or code: A command, key or check exists when code reads its result or it supplies a fact the model cannot see; the rest is prose, the default when unsure.
rule/0026  accepted  Step bodies are fetched on demand, not pasted into spawn prompts: A step's body is fetched when the step runs rather than pasted into a spawn prompt, so a run's context grows with its graph, not with the sum of its step bodies.
rule/0027  accepted  A hermetic render repeats byte for byte: With macros stubbed and the config merge pinned to core and project levels, a render is identical on any machine.
rule/0028  accepted  Vault artefacts are plain markdown with YAML frontmatter: Every artefact a run writes into the project vault is plain markdown with YAML frontmatter, readable in Obsidian.
rule/0029  accepted  Graph and render problems are reported in band, never as crashes: A graph or render problem surfaces as a STOP or Note notice in the rendered output at exit 0, never as a crash.
value/0001  -  Curated self-learning: The system gets better from its own runs, but only through the user and when the user wants it: a lesson becomes a rule after the user takes it, not after every run.
value/0002  -  Minimal effective context: A step gets only what it needs.
value/0003  -  Single source: Each fact, decision and piece of structured data lives in one place and is referenced or rendered from there; a decision is kept together with its reason.
value/0004  -  Analysable history: Plans, runs and their outcomes are kept across every project, so the history can be analysed: practices taken over from one project to another, benchmarks, quality comparison, problem analysis.
value/0005  -  Stack-agnostic core: The core knows nothing about a stack or a project; specifics live in the global and the project tiers.
value/0006  -  A framework for playbooks: Booping is a framework a user digitises their own processes with — config, templates, primitives, the CLI, playbooks and evals for their steps.
value/0007  -  Plans run to the end: The agent carries a plan through to the end on its own unless force majeure stops it.
value/0008  -  Effective human review: Every step where a human takes part is convenient and effective for that human.
value/0009  -  Adjustable control: The human can review the system deeply, or give the agent more freedom to act inside the values and boundaries.
value/0010  -  Proven to work: We know the system works as it should and can guarantee it high enough to call it reliable.
value/0011  -  Everything in one place: Everything is plain files, easy to look at from one place — for example Obsidian; symlinks back to the project repos keep it together.
value/0012  -  Quality at a rational cost: Booping is a work tool for professionals, so the quality of the result matters.
value/0013  -  Guides to the goal: The system is clear to the user and leads them to the goal by the hand, while letting a professional step aside and get there their own way.
value/0014  -  Comfort for non-technical users: How comfortable booping is for people without a strong technical background is not optimised for; they are not its audience.
