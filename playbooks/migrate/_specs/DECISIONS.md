- `[2026-08-05 07:35]` Consequence flagged by the runner for the downstream core plan: a run touches two locations — the vault (files transformed) and the repo's `.booping` (id advanced) — so "clean tree" and "commit per migration" need to state which repo they mean.

Report the issue concretely (which id, what failed) and suggest a fix — explicitly including a manual fix the user performs by hand. No silent rollback, no skipping ahead. Recorded id and commits stay at the last fully applied migration; the user re-runs after resolving.
- `[2026-08-05 07:38]` Execution model: the user sees each migration as a prompt executed as an **isolated step**. The apply phase is not one step looping internally — each pending migration is applied by its own context-fresh isolated unit whose entire instruction is that migration file's prompt + commands. Implies a repeat-per-pending-migration shape for decompose, running **sequentially in id order** (never parallel, since each migration assumes the previous landed), with a failure in one unit halting the sequence.
